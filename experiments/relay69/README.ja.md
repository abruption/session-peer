# #69 ペアリングデバイス中継ラボ

ローカルの #47 コミット `993d04d` に基づく実験的かつフィクスチャ専用のコードです。**本番レシーバー、プラグイン、またはインストール済みCLIコマンドではありません。** 通常のパッケージ、ローカル/SSHの動作、およびインストール済みバージョンは変更されません。ネイティブのClaude/Codexセッション、受信箱、キュー、モデルの認証情報やクォータは使用されません。

## ローカルでの再現

Python 3.11以上およびTLS 1.3対応のOpenSSLが必要です。テストされた環境は、macOS Python 3.14/3.13およびUbuntu arm64 Python 3.12です。

```sh
python3 -m venv /tmp/session-peer-relay-lab
/tmp/session-peer-relay-lab/bin/pip install -r experiments/relay69/requirements.txt
/tmp/session-peer-relay-lab/bin/python -m unittest tests.test_relay69 -v
```

テストでは、ループバックTCP、実際のTLS、ローカルWebSocket中継、および破棄可能な状態を使用します。オプションの依存関係がない場合、通常のunittest探索はこのモジュールをスキップします。この実験はwheelやsdistには含まれません。インポートによってリスナーが起動することはありません。

## コンポーネントと境界

- `identity.py`: ローカルで生成されたP-256秘密鍵と有効期間の短い自己署名証明書。鍵/状態は0600/0700であり、招待状に含められたり中継にコピーされたりすることはありません。これはファイルシステムによる保護であり、本番OSのキーチェーンではありません。
- `wire.py`: Python/OpenSSLのMemoryBIOを使用した、TCPまたはバイナリWebSocketフレーム上のTLS 1.3/ALPN。クライアントは招待された証明書を明示的に信頼し、ピン留めします。ペアリングされたレシーバーは、list/sendの前に認識されたクライアント証明書を要求します。未知の未認証クライアントは、接続ごとに1回のみの招待予約を試行できます。公開中継URLにはWSSが必要です。平文のWSはループバックテストに限定されます。HTTPおよびWSのリダイレクトは拒否されます。
- `store.py`: 10分間の1回限り有効な招待予約、保留中/ペアリング済み/失効済みのデバイス状態、エージェントデータベースから独立した実行ジャーナル。ペアリングは、相互TLSによって提案された鍵が証明された後にのみコミットされます。保留中のイニシエーターは、同じ鍵を使用して失われたコミット応答を照合できます。失効はアクティブなチャネルを切断します。ローテーションは失効と新しいペアリングであり、シームレスな更新ではありません。
- `relay.py`: ロール/ルームスコープの入場認証情報が120秒間有効なHttpOnlyセッションCookieを発行します。認証はアップグレードの前に行われます。中継は暗号文のみを転送し、エンドポイントの鍵を保持しません。ルーティング/ロール、IP、時刻、長さ、および暗号文を認識します。Cloudflare/Caddyは外部TLSメタデータ**および入場認証情報/Cookie**を認識しますが、内部TLSの平文や鍵は認識しません。外部認証はエンドツーエンドのアイデンティティではなく、ピアTLS検証の代わりにはなりません。
- `app.py`: 受信したすべての操作は #47 の `LocalTransport` および1つの明示的にインスタンス化された決定論的フィクスチャアダプターを経由します。通信操作はprobe/list/send/statusです。任意のコマンド、パス、ネイティブアダプター、またはwakeは利用できません。リクエストはバージョン、両方のアイデンティティ、UUID、有効期限、操作、および本文をバインドします。TLSチャネルがレコードの整合性とリプレイ保護を提供します。

ジャーナルは、フィクスチャアダプターを呼び出す前に保留中の意図をコミットします。同じ本文を持つ同一のピア+メッセージIDは保存された結果を返します。異なる本文は拒否されます。アダプターの呼び出しと結果コミットの間のクラッシュは不明のままとなり、自動的に再実行されることはありません。これは活性よりも最大1回の試行を優先します。これはネイティブの厳密に1回の配信では**ありません**。`submitted` は `consumptionConfirmed` とは分離されており、後者はfalseのままです。`relayAttached` はキャリアへの接続を示します。認証されたエンドポイントプローブのみがレシーバーの準備完了を確立します。

自動ルートは認証済みの直接プローブと中継プローブを競合させ、両方が同じ選択サイクルで完了した場合は直接接続を優先します。メッセージは1つの勝者にのみ送信されます。送信後の失敗によってルートが切り替わったり、再送されたりすることはありません。結果が不明な場合は、元のメッセージIDでstatusを使用してください。

## 明示的なコマンド

実験用venvを使用してワークツリールートから実行します:

```sh
python -m experiments.relay69 init --state /private/test/receiver
python -m experiments.relay69 invite --state /private/test/receiver \
  --out /private/test/invitation.json --direct 127.0.0.1:3769
python -m experiments.relay69 serve --state /private/test/receiver \
  --bind 127.0.0.1 --port 3769 --seconds 1800
python -m experiments.relay69 pair --state /private/test/client \
  --invite /private/test/invitation.json --route direct
python -m experiments.relay69 request --state /private/test/client \
  --peer RECEIVER_FINGERPRINT --route direct --op send --message fixture-only
```

ペアリングの前に、招待状の証明書フィンガープリントとレシーバーの `init` 出力を、個別に信頼された管理経路を通じて比較してください。このラボでは、公開招待情報に既存のSSHを使用し、使い捨てシークレットにプライベートファイルを使用しました。招待状、入場シークレット、またはCookieをログやURLに貼り付けないでください。
`request --op status --message ORIGINAL_MESSAGE_ID` は不確実な結果を照合します。
`revoke --state RECEIVER_STATE --peer CLIENT_FINGERPRINT` はそのテストクライアントを失効させます。

中継モードの場合、git外でロールごとに1つずつ、2つのランダムな256ビット入場認証情報をプロビジョニングします。中継の `--accounts` ファイルは、`{hash: SHA256(credential), room: test-room, role: receiver|client}` のJSON配列です。エンドポイントは0600の `--admission-file` で自身の認証情報のみを受け取り、相手のプライベートTLS鍵を受け取ることはありません。inviteとserveの両方に `--relay wss://HOST/v1/connect` を追加し、`pair --route relay` を使用します。レシーバーとクライアントは両方ともアウトバウンド接続します。中継コマンドは `--bind`、`--port`、`--accounts`、および `--seconds` を受け付けます。

公開トライアルでは、専用のホスト名、既存のCF/KR TLS終端、およびKRからUSへのtailnetアップストリームを使用しました。公開設定はインフラストラクチャ固有であり、このリポジトリによって自動的にプロビジョニングされることはありません。デプロイされたトライアルは残っていません。

## 運用制限

中継は、10接続、毎秒20件のHTTP入場/アップグレードリクエスト、100個のアクティブなCookie、256 KiBのフレーム、4フレームの受信ウォーターマーク、32 KiBのトランスポート書き込みウォーターマーク、2秒の転送期限、および合計32 MiBの転送バイト数を許可します。TLS JSONメッセージは64 KiBに、メッセージ本文は32 KiBに制限されます。レシーバーは接続を8に、接続あたりのリクエストを100に制限します。そのジャーナルは、重複排除履歴を暗黙のうちに破棄するのではなく、10,000レコードで停止します。これらの制限はテスト用のバジェットであり、調整された製品の保証ではありません。

サービスのライフタイムは最大30分です。公開バックエンドでは、独立したsystemdランタイム制限、DynamicUser、ケーパビリティなし、読み取り専用コード、ProtectHome、明示的な禁止ディレクトリ、専用のtmp/devices、256 MiBのメモリ、50%のCPU、64個のタスクも使用されました。Cgroup IPルールにより、USバックエンドへのアクセスはKRのみに許可されました。サンドボックスの事前確認により、他のホームや製品ディレクトリが読み取り不可能であることがアサートされました。新しいファイアウォールルール、DNSレコード、永続アカウント、またはグローバルPythonパッケージはインストールされませんでした。Macのフィクスチャクライアントは個別のstate/venvを使用しました。これらがLinuxサンドボックスのOS分離を備えているとは主張されていません。

実際のアプリケーションでは、より堅牢なデバイスライフサイクル/UX、送信元に束縛された入場設定、デバイスごとのクォータ、オフライン回復、依存関係とプロトコルのレビュー、およびプラットフォームサービス/鍵ストレージの設計が必要になります。受領契約は、中継への接続、エンドポイントによる受領、およびネイティブの送信を引き続き区別しなければなりません。[測定レポート](REPORT.ja.md)を参照してください。
