# session-peer v1.0.0-rc.3

这是准备中的候选版本，并非发布公告。RC3 保留 RC2 契约，针对 #161 跟踪的间歇性公共中继路由失败。除明确测试预发布版外，稳定版用户应继续使用 v0.9.2。

## RC2 之后的变更

- #162：路由失败继续保留 `no_authenticated_route`、`retryAllowed: false` 和 `consumptionConfirmed: false`，并为每次尝试报告经过清理的阶段、原因、耗时以及 WebSocket 关闭代码与来源。control 与 admission 设置超时只在应用提交前使用新的 admission 重试一次，绝不重发代理消息。
- #162：可选的 `--diagnostic-events` 输出仅含元数据的接收端生命周期事件与中继房间事件，中继指标新增房间、attach 与过期计数器。诊断默认关闭。
- #168：若等待房间已开启至少 1 秒后被中继正常关闭，接收端会在 0.5 秒后重连，而不会增加退避时间。中继连接使用 10 秒的 WebSocket ping 间隔与超时，停滞连接约 20 秒即可检测到，而不是约 40 秒。
- #168：中继指标新增统计被拒绝重复连接的 `receiverRoleBusy` 和 `clientRoleBusy`。
- #163 的离线回环复现表明，这些变更可缩短放大停滞路径影响的重连空档。它们不能修复停滞的网络路径，也不能证明 #161 已解决。

## 升级说明

- 没有模式、状态或策略迁移。请保留设备身份、固定信息、回执、墓碑记录与防重放状态，不要删除状态或重发结果未知的消息。
- 请将中继与配对的两个端点升级到同一版本。新增的指标与事件均为增量添加，详见[配对设备指南](../paired-devices.md)。
- 原生 Windows 核心与 MCP 仍受支持。接收端/中继运行时需要 Unix 或 WSL 以及 Python 3.11+。

## 发布后安装

在两个配对端点上使用相同的包管理器和精确版本。现有托管安装应在原环境内升级，不要替换为其他安装管理器。

```bash
# Unix / WSL with relay and MCP
pipx install 'session-peer[relay,mcp]==1.0.0rc3'
# Native Windows core and MCP, without relay
pipx install 'session-peer[mcp]==1.0.0rc3'
```

Python/PyPI 版本为 `1.0.0rc3`，GitHub 标签为 `v1.0.0-rc.3`。无依赖的核心需要 Python 3.9+，MCP 需要 Python 3.10+。

## 证据与剩余条件

RC2 的四小时观察在第 172 分钟中断且没有完成记录，并记录了公共中继失败，因此不是通过的 soak。离线复现只能证明机制，不能确定实际故障原因。

在精确的已发布 RC3 通过五主机观察之前，请保持 #161、#163、#164 开启。不要将 `posted` 或 `queued` 视为已消费；没有独立观察到的 ACK 时，`consumptionConfirmed: false` 依然如实。

## 发布后验证计划

1. 验证精确的已发布标签与提交、wheel 与 sdist 哈希以及全新安装。GitHub 保持为预发布而非 Latest，稳定版升级必须继续选择 v0.9.2。
2. 在 Mac mini、MacBook、quintet-desktop（原生与 WSL）、KR 和 US 安装精确的 RC3 之前，备份安装文件并使用经批准的一致状态快照。保留生产身份与防重放状态，不要悄然替换安装管理器。
3. 由始终记录 `complete` 或 `aborted` 的独立监督进程执行五主机四小时观察 (#164)：每分钟健康检查；对同一接收端的直接与中继 probe 间隔至少 5 分钟；启用 `--diagnostic-events`；每分钟记录 `receiverRoleBusy` 和 `clientRoleBusy`；在 T0/T2h/T4h 使用新令牌获取独立 ACK；在 T2h 重启中继一次，恢复目标为 60 秒以内。
4. 按诊断阶段记录失败。无法解释的失败、缺失的 ACK 或未完成的观察都会阻止升级；不要仅因 PR 合并或 PyPI 发布成功就关闭 RC3 里程碑。

## 发布边界

- 准备工作不授权打标签、发布、替换设备或重启生产环境；这些需获得批准后单独执行。
- Antigravity 仍处于实验阶段。托管中继/OAuth 的健康状态与软件包发布无关。
- 切勿为获取 ACK 而更改入站权限、重试含糊的发送、在报告中暴露凭据，或将对端请求视为用户的直接批准。
