# session-peer v1.0.2

这是继 v1.0.1 之后以稳定性为重点的维护版本。本地/SSH 核心命令在 Python 3.9+ 上仍无第三方依赖。Relay 和 MCP 保持可选，Antigravity 桥接仍为实验功能。

## 变更

- Control 在变更被拒绝或失败后保持 health 与公开状态一致(#200)。提交前检查读取端的 1 MiB UTF-8 容量限制，不丢弃吊销记录(#208)。
- Control 可认证回环反向代理提供的客户端身份以用于限流；任意转发头仍不可信(#202)。
- 恢复时将未知原生结果保持为未解决，不把已完成的日志条目当成送达证据(#201)。批准模式 v2 对 `peerGeneration` 签名并保留密钥轮换代数(#203)。
- 独立安装器先暂存下载并验证 CLI，再原子替换运行时；下载或验证失败时保留现有安装(#204)。
- 显式 Codex wake 和 MCP CLI 清理会回收其拥有的 POSIX 进程组，包括不响应 TERM 的后代(#205, #206)。
- SSH 在启动前检查经过 shell 引用的 UTF-8 命令大小，包括编码及消息封装开销，拒绝超限命令(#207)。
- SQLite 备份 fixture 显式关闭连接(#209)。Relay 设置失败会给出允许列表中的可操作提示，不会自动安装依赖、登录、配对或重发(#210)。
- 兼容技能快照同步到 v0.3.1(#199)，并更新固定的 GitHub Actions。单独安装的技能继续使用原更新管理器。

## 安装与升级边界

使用现有安装管理器，不要悄悄替换另一种安装方式。

```bash
pipx upgrade session-peer
# New Unix / WSL installation with optional Relay and MCP:
pipx install 'session-peer[relay,mcp]==1.0.2'
```

核心要求 Python 3.9+，MCP 要求 3.10+，Relay 接收端/服务器要求 Unix 或 WSL 上的 Python 3.11+。由服务管理器启动的 macOS/Linux 接收端仍需在服务 PATH 中提供 Codex，或配置运维人员管理的 `codexBin`。发送前用 `--dry-run` 确认目标。

- 生成 v2 批准前，先升级执行恢复提交的设备：旧版本仅接受 v1。已知归档密钥代数时仍可使用旧批准，但恢复不会猜测轮换密钥的代数。激活前将已有恢复计划与归档回执核对；恢复执行不会改写旧计划。
- 认证代理身份需要单独配置 `SESSION_PEER_TRUSTED_PROXY_TOKEN_FILE`，并让代理覆盖两个专用头。默认仍按 socket 地址限流。安装软件包不会改变代理设置或信任任意 CDN 头。
- 已超限的 Control 数据库会保持不健康，直到安全解决容量问题；新限制不会删除历史记录。Control 部署与 Python CLI 安装相互独立。
- 原子替换只针对运行时文件，不是跨所有文件的事务，也不是后续技能管理器失败后的回滚。POSIX 清理不覆盖逃离所属组的进程和远程 SSH 进程；Windows MCP 只终止直接子进程。

## 验证与已知限制

发布准备关卡包括回归测试、文档与翻译检查、生成源码检查、归档检查、可复现构建和干净的 wheel/sdist 安装。这不是新的四小时实环境测试，也不保证托管 Relay/OAuth 可用。历史 RC4 证据属于 v1.0.0，不应当作本维护版的验证结果。

#161 仍然开启：公共路径间歇停滞的根因及责任方尚未确定，本版本不声称修复该网络路径。`posted`、`queued` 和 `submitted` 是提交证据，不是消费或 ACK。未知结果绝不能自动重发。软件包发布、设备安装和生产重启仍是独立操作。
