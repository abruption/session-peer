# session-peer v1.0.3

这是继v1.0.2之后的安全与稳定性维护版本。本地/SSH核心在Python 3.9+上仍不需要额外依赖。Relay和MCP仍为可选功能，Antigravity桥接仍处于实验阶段。

## 安全修复

准备发布时，五项公告均未分配CVE编号。使用GHSA标识符继续发布。

- [GHSA-9x52-82cv-4c22](https://github.com/abruption/session-peer/security/advisories/GHSA-9x52-82cv-4c22)：OpenSSH运行前验证SSH目标及完整的传入选项列表，并对远程参数进行shell引用。
- [GHSA-4rvw-q2vm-v4x3](https://github.com/abruption/session-peer/security/advisories/GHSA-4rvw-q2vm-v4x3)：配对要求基于证书的初始principal，或轮换密钥已有的可信绑定。
- [GHSA-6xwm-5p7g-8v8q](https://github.com/abruption/session-peer/security/advisories/GHSA-6xwm-5p7g-8v8q)：Relay将无效路径/连接与会话签发预算分离，并增加有界的每来源握手限制。
- [GHSA-2hjv-35jg-gghm](https://github.com/abruption/session-peer/security/advisories/GHSA-2hjv-35jg-gghm)：托管Control的设备码签发仅接受指定客户端字段，限制待处理代码并清理过期记录。
- [GHSA-646x-xjw9-mf6x](https://github.com/abruption/session-peer/security/advisories/GHSA-646x-xjw9-mf6x)：托管Control阻止bearer凭据升级为cookie，并对批准和登录会话管理实施cookie/Origin检查。

升级客户端及自行托管的Relay/Control服务。源代码修复不代表托管服务已部署补救措施。现有配对绑定不会自动审计或删除：运营人员必须检查并撤销不可信绑定、重新配对。在反向代理后配置经过认证的客户端来源边界和边缘准入限制；多个来源仍可能耗尽全局预算。

## 稳定性与发布变更

- SSH保留有效的带内结果和超时前捕获的响应；不确定的发送保持unknown，不得自动重试 (#249)。
- MCP在升级终止操作前给所拥有的wake进程留出清理时间 (#250)。
- 接收端隔离未认证任务的准入，并限制清理和关闭时间 (#251)。
- PyPI发布要求明确的环境审核；定期依赖审计独立于产品CI运行 (#252, #253)。
- 原生消息保留字面上的前导短横线，并在启动前拒绝过长的Windows命令行 (#254)。
- 面向人的输出转义终端控制字符，结构化JSON保留原始数据 (#255)。
- SSH单文件更新验证暂存文件、串行化替换、防止过期降级，并保留确定或不确定的提交回执 (#256)。
- 单文件安装/更新认证不可变发布资产与来源证明；发布安装探测验证隔离环境中实际安装的包 (#257)。
- Control登录在创建24小时后绝对过期；浏览器会话列举/撤销使用独立速率预算 (#258)。

## 安装与升级边界

使用已有的安装管理器。pipx示例：

```bash
pipx upgrade session-peer
# New Unix / WSL installation with optional Relay and MCP:
pipx install 'session-peer[relay,mcp]==1.0.3'
```

核心需要Python 3.9+、MCP需要3.10+、Relay接收端/服务端需要Unix或WSL及Python 3.11+。服务管理的接收端需要服务PATH中的Codex或运营人员拥有的codexBin绑定。发送前用--dry-run验证。

SSH选项兼容范围有意缩小：仅接受文档允许列表中的连接选项。执行本地命令或选择其他配置文件的ProxyCommand、LocalCommand和-F等选项会被拒绝。可信的用户自有OpenSSH配置仍是运营边界。验证后的单文件安装需要已认证GitHub CLI的attestation验证，不会回退到旧的未签名版本或开发main。

升级时，现有滑动Control会话会被限制为原始创建时间后24小时，可能需要立即重新登录。设备撤销与账户登录会话撤销是独立操作。若设备或登录凭据丢失，应同时撤销两者；无法识别相关登录时撤销所有其他会话。

## 验证与已知限制

发布门禁检查回归、文档/翻译、生成源码、归档、可复现性、干净环境安装及依赖审计。这些是门禁要求，不是新的实时四小时测试证据。历史RC4验证及独立ACK 20/21属于v1.0.0。私有公告分支检查不能替代整合后的公开main准确提交在发布前通过的发布门禁。

#161仍未确定公开路径停滞的根本原因。posted、queued和submitted是提交证据，不是消费或ACK。未知结果不能授权自动重发。包发布、托管补救部署、设备群安装和生产服务重启是独立操作。
