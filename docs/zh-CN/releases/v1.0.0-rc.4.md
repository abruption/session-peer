# session-peer v1.0.0-rc.4

RC4 是对部分发布的 RC3 使用新版本进行的修正发布。PyPI 接受了 RC3 wheel，但 sdist 上传因多次 HTTP 502 响应而失败。RC3 不能用于正式版升级。RC4 只更改软件包版本和发布文档，运行时行为仍是经过审查的 #162 与 #168 实现。除非明确测试预发布版，稳定版用户应继续使用 v0.9.2。

## 自 RC2 以来的变更

- #162 保持失败时拒绝的路由契约，同时增加每次尝试的匿名化阶段和可选诊断事件。control/admission 的设置重试仅发生在应用提交前，绝不重发消息。
- #168 在正常 idle 到期后将接收端重连延迟维持在 0.5 秒，对 Relay 连接使用 10/10 秒 ping，并增加 receiverRoleBusy 与 clientRoleBusy 计数器。
- #163 的离线复现仅表明停滞路径的放大效应降低，并不证明路径已修复或 #161 已解决。

## 完整发布后安装

在两个已配对端点上使用现有包管理器安装精确候选版本。不要替换安装管理器，也不要从 RC3 不完整的文件集中安装。

```bash
# Unix / WSL with relay and MCP
pipx install 'session-peer[relay,mcp]==1.0.0rc4'
# Native Windows core and MCP, without relay
pipx install 'session-peer[mcp]==1.0.0rc4'
```

Python/PyPI 版本是 1.0.0rc4，GitHub 标签是 v1.0.0-rc.4。核心需要 Python 3.9+，MCP 需要 3.10+，接收端/Relay 运行时需要 Unix 或 WSL 上的 3.11+。

## 证据与剩余关口

RC2 的四小时活动在第 172 分钟结束，未留下完成记录。在精确且完整发布的 RC4 通过五主机验证前，保持 #161、#163、#164 开启。posted 或 queued 不等于已消费的 ACK；没有独立观察时，`consumptionConfirmed: false` 才是正确结果。

## 发布后验证计划

1. 验证已发布的标签和提交、PyPI 两个文件的哈希、wheel 与 sdist 的全新安装、预发布状态，以及稳定版 v0.9.2 的 latest 状态。
2. 在 Mac mini、MacBook、quintet-desktop（原生与 WSL）、KR、US 安装精确 RC4 前，备份安装文件并保留经批准的一致性状态快照。保留设备身份、策略和防重放状态。
3. 使用独立进程运行 #164 五主机四小时活动，并确保留下 complete 或 aborted 记录：每分钟 health、每个接收端至少间隔五分钟的 probe、诊断事件、每分钟 receiverRoleBusy/clientRoleBusy、T0/T2h/T4h 独立 ACK，以及 T2h 一次 Relay 重启并以 60 秒内恢复为目标。
4. 按阶段分类每次失败。无法解释的失败、缺失的 ACK 或未完成的运行均阻止升级。不要仅因发布或 PR 合并成功就关闭里程碑。

## 发布边界

准备本身不等于发布或全设备验证。Antigravity 仍属实验功能，托管 Relay/OAuth 的健康状态与包可用性是两回事。不要重发结果未知的消息，也不要为了强制 ACK 改变接收权限。
