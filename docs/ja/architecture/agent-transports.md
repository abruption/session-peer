# ADR: 内部エージェントおよび実行トランスポート規約

ステータス: v0.8 後のリファクタリング（#47）で承認済み。これは内部ソースの規約であり、公開されている外部プラグインの ABI ではありません。パッケージバージョンは、別途準備されるリリースまで 0.8.0 のままです。

## 決定事項

依存関係のない `session_peer.py` スタンドアロンアーティファクトを維持し、そのファイル内で規約を定義します。SSH はそのソースを送信先側の `python3 -` にストリーミングします。通常のitiertリモート操作では、送信先に session-peer サービスやパッケージがインストールされている必要は依然としてありません。現時点でランタイムをインポート可能なファイルに分割すると、バンドルビルダー、リモートモジュールのインストール、または第 2 の配布メカニズムが必要になります。エージェント/トランスポートの境界を検証するためにこれらは不要です。

エージェントは、ネイティブのアイデンティティ、検出、検証、送信、診断、エージェント固有のコマンドオプション、および表示を担当します。トランスポートは、それらの操作がどこで実行されるかを担当します。`LocalTransport` は登録されたアダプターを呼び出します。`SshTransport` は送信先を解決し、安全にクォートされた既存の単一ソース SSH プロトコルを呼び出します。受信側は同じ CLI を解析し、そのローカルアダプターを呼び出します。SSH はエージェントではありません。

初期レジストリには Claude、続いて Codex が明示的に含まれます。CLI の選択肢、一覧取得、送信、doctor、Reply-To の検証、および MCP エージェントポリシーはそのレジストリを使用します。MCP は引き続き CLI のポリシー適用サブプロセススクライアントであり、登録によって送信/wake 権限が付与されることは決してありません。アップデートのデプロイは、依然としてエージェントの送信とは区別されます。

## 根拠と互換性

- Claude の検出は PID/名前/受信トレイの証拠を生成し、ネイティブソケットに書き込みます。書き込みの完了は消費の証明ではありません。
- Codex はネイティブのキューおよび app-server インターフェースを使用します。1 つの UUID が複数のホームに存在する可能性があるため、アイデンティティは UUID ごとに集約するのではなく、ホストとホームを保持します。マルチホームのインベントリ、曖昧さのチェック、およびアクティブライターの検証は、Codex の実装内に残されます。呼び出し側のデフォルト値は、リモート受信側のアクティブなホームに関する証拠ではありません。
- ネイティブキューへの受け入れは、wake の失敗より前に行われる場合があります。キュー ID、送信ステータス、および wake ステータスを含むネイティブペイロードを保持し、自動的に再試行しないでください。
- Wake はオプションであり、以前に検証されたランタイムとライフサイクルに制限されたままです。待機および確認応答は、両方のアダプターでサポートされていません。
- ホストアイデンティティ、送信者エンベロープ、および返信ルートの正規化はエージェントから独立しています。送信側でメッセージエンベロープを一度構築し、その既存の base64 表現を SSH 経由で送信します。

既存のオプション、通信フィールド、応答エンベロープの schemaVersion、順序、および終了コードは変更されません。追加された例外は `doctor.capabilities.agents` であり、登録された名前を boolean の `list`、`send`、`wake`、`wait`、および `ack` のサポートにマッピングします。これらは実装されたメカニズムを説明するものであり、現在の認証情報、受信トレイの利用可能性、モデルの準備状況、または送信先の権限を示すものではありません。`doctor.capabilities.replyObservation` は以前の意味を保持します。

リモート一覧取得の部分的な失敗でも `not_installed` の検出ステータスを受け入れます。そうしないと、オプションの Codex がインストールされていない場合に、別のエージェントの失敗診断が破棄される可能性があるためです。`submitted: true` を持つ失敗したリモート送信も同様に、その ID を破棄するのではなくネイティブ結果を保持します。Reply-To があるエージェントを主張しながら、別のエージェントの登録済みプレフィックスをターゲットにすることはできません。

## 規約と信頼境界

`ADAPTER_CONTRACT_VERSION = 1` は JSON 応答の schemaVersion とは独立しています。レジストリは登録前に名前、正確な規約バージョン、ケーパビリティ、およびメソッドを検証し、重複は拒否されます。`SessionIdentity` はエージェント、ホスト、識別子、およびオプションの Codex ホームを記録します。`ExecutionContext` は送信先アイデンティティと解析済みオプションを提供します。これらはプロセスローカルな値であり、新しい通信プロトコルではありません。ネイティブの結果フィールドがフラット化されて失われないよう、検出と送信は型付きディクショナリ規約を維持します。

`AdapterError` は既存の CLI エラーから派生し、agent/reason フィールドを追加します。規約エラーは `invalid_adapter_contract`、`duplicate_agent`、`unknown_agent`、`unsupported_capability`、または `invalid_target` を使用します。不正な形式の検出および診断は `invalid_adapter_result` を使用します。予期しない操作例外は、例外テキストをエコーバックすることなく `adapter_failed` として包含されます。ネイティブの送信がすでに行われた可能性があるため、予期しない送信エラーまたは不正な形式の送信結果は、再試行なしの `outcome_unknown` になります。既存の意図的な CLI/ネイティブエラーとその構造化された詳細はそのまま維持されます。

検出では、集約の前に各アダプターの結果を検証します。あるアダプターの障害によって、他のアダプターの成功した行や診断情報が破棄されてはなりません。トランスポートが復帰したという理由だけで消費を主張できるアダプターはありません。

エントリポイントの検出、名前によるインポート、プラグインディレクトリのスキャン、またはメッセージ駆動型のロードは存在しません。メッセージ、CLI 引数、URI、または MCP ポリシー内の名前によってコードがインストールされたり実行されたりすることはありません。未知の明示的なエージェントは失敗します。通常のターゲット文字列内の未登録プレフィックスは、互換性のためにリテラルの Claude 名のまま扱われます。同様に `claude:` プレフィックスも依然としてリテラルの Claude 名の一部です。Codex および新しく登録されたアダプターは、それぞれの登録済みプレフィックスを使用します。

将来の外部プラグインには個別の設計が必要です: オペレーターによる明示的なインストールと許可リストへの登録、パッケージの所有権と依存関係の隔離、バージョンネゴシエーション、エラーの包含、およびインプロセス Python プラグインが信頼されたコードを実行するという事実の文書化です。本変更ではサンドボックスや外部ロードフラグは提供されません。

## 検証

`tests/adapters/test_adapters.py` は、共通の Claude/Codex/フィクスチャ規約、第 3 のエージェントの CLI および Reply-To ルーティング、ケーパビリティ、互換性のない登録、不正な結果、例外の包含、MCP ポリシー、およびネイティブ送信数を検証します。ソース登録されたフィクスチャは、ストリーミングされるプログラムのテスト用コピーにのみ挿入され、既存の SSH シリアライザーを介して新しい Python サブプロセスで実行されます。そのテストのために本番環境のディスパッチ編集、外部プラグインローダー、アクティブなモデルアカウント、SSH 接続、またはメッセージ配信は必要ありません。

既存のトランスポート、ネイティブソケット、キュー、マルチホーム、返信、MCP、および wake スイートは互換性のベースラインのままです。パッケージおよびスタンドアロンのインストールテストにより、単一ファイルおよびオプションのエクストラの配布境界がそのまま維持されていることが確認されます。
