# リレーライフサイクルの堅牢化（開発）

これらの変更は #69 に向けた開発中のものです。公開された RC ではなく、24時間の稼働ゲートや実際の OAuth プロバイダー検証を通過していません。

## 安定したデバイスと明示的なローテーション

初期の証明書フィンガープリントは論理デバイス ID として維持されます。公開鍵バージョンには個別のフィンガープリントと世代が存在します。ポリシー、ルート、およびリクエスト受領証は、レシーバーキーの変更をまたいでも論理 ID に紐付いたままとなります。追加的な SQLite マイグレーションにより、既存の v0.9 アイデンティティと受領証が保持されます。

ローテーションを行う前に、デバイスレシーバーおよびその状態を使用している他のコマンドを停止してください:

```sh
session-peer device rotate --state /private/device-state \
  --operation-id REPLACE-WITH-A-FULL-UUID --route direct
session-peer device rotation-status --state /private/device-state
```

失われた応答から回復する際は、操作 ID を維持してください。不明な結果を解決するために新しいローテーションを開始してはなりません。ペアリングされたすべてのピアは、明示的に設定された到達可能なレシーバールートを持ち、`identity-rotation-v1` をサポートしている必要があります。既存の `device routes` コマンドでルートを更新してください。レシーバーはオフラインのクライアント上で透過的にピンをローテーションすることはできません。まずそのクライアントレシーバーをオンラインにしてください。

Prepare はピン留めされた TLS を介して古い鍵を証明し、新しい鍵で作成された署名を検証します。Commit には新しい鍵による TLS 接続が必要です。移行中、保留中および退役済みの鍵は、プローブ、受領証ステータス、およびローテーション調整アクセスのみが許可されます。以前にコミットされた古い鍵には10分間の回復ウィンドウがあり、メッセージを送信することはできません。失効はこのウィンドウより優先されます。新しいリクエストや競合によって同一世代に対する2回目のローテーションが作成されることはありません。ローカルのアクティベーションは、記録されたすべてのピアがコミットした後にのみ行われます。失敗した試行では同じプロポーザルと秘密鍵が保持されます。

デバイス状態ロックは、通常のコマンドやレシーバーが状態を保持している間のローテーション/バックアップを排除します。別のレシーバーロックにより、2つのローカルレシーバープロセスが同じ状態を使用することを防ぎます。これらはローカルファイルシステムのロックであり、分散リースではありません。稼働中のアイデンティティを2台目のマシンにコピーすることはサポートされていません。

## ジャーナルの制限と回復

```sh
session-peer device diagnostics --state /private/device-state
session-peer device backup --state /private/device-state \
  --policy /private/policy.json --out /private/new-snapshot
session-peer device restore --state /private/new-restored-state \
  --backup /private/new-snapshot
```

Diagnostics は、グローバルな10,000リクエスト制限、残りの行数、保留中の不明な結果、SQLite/WAL のサイズ、および空きディスク容量を報告します。通知、警告、重大のしきい値はそれぞれ 70%、85%、95% です。容量上限に達すると新しい送信は拒否されますが、既存の受領証および管理機能は引き続き利用可能です。空き容量を確保するために受領証のエビデンスが削除されることはありません。容量予約と受領証の作成はトランザクションとして行われます。

バックアップには排他的な状態ロックが必要であり、アイデンティティバージョン、ポリシー、一貫性のある SQLite スナップショット、およびマニフェストが含まれます。出力はキーを含むプライベートな**暗号化されていないステージングディレクトリ**です。保存には承認された暗号化バックアップシステムを使用してください。ソース管理を通じてディレクトリを公開または移動しないでください。状態をバックアップしても、リレーや OAuth 制御サービスに鍵がコピーされることはありません。

復元はプライベートなステージングディレクトリを準備し、永続的な回復マーカーをコミットした後にのみ、ターゲットをアトミックに公開します。中断されたステージングは使用できません。既存の受領証は引き続きクエリ可能です。欠落している受領証は、実行されなかったことを証明するのではなく、不明を返します。送信および受信、キーローテーションの変更、新しいペアリング/登録はすべてブロックされたままになります。受領証ステータスのクエリは引き続き利用可能です。この安全策を解除する単一コマンドのオーバーライドは存在しません。回復を計画する前に、スナップショット作成後のネイティブな影響を調整し、古いアイデンティティを失効/フェンスしてください。この開発実装では、完全な鍵紛失回復ワークフローはまだ提供されていません。

## 制御データベースのアップグレード

制御データベースには Better Auth のスキーマとは別に、独自のマイグレーション台帳があります。新規インストールおよびスキーマを変更するすべてのアップグレードでは、HTTP サービスを開始する前にコンパイル済みマイグレーションを明示的に実行する必要があります:

```sh
node dist/server/migrate.js
```

最初にパブリッシャーとリレーを停止してフェンスしてください。SQLite データベース、署名鍵、公開状態、リプレイ最高水位状態を含む保護された一貫性のあるスナップショットを取得し、制御サービスのアイデンティティとして通常の保護設定と排他的 writer lock を使用してコマンドを実行します。マイグレーションはトランザクション型かつ冪等であり、安定した principal、世代、失効 tombstone、操作受領証、単調増加する公開リビジョンを保持します。

通常の起動は検証のみを実行します。古い、部分的、将来版、または破損したスキーマは DDL を実行せず `migration_required` で失敗します。マイグレーションを `ExecStartPre` に追加したり、マイグレーション台帳を削除したり、失敗後に古いスナップショットを自動復元したりしないでください。スタックを停止したまま、フェンスされた復旧をレビューしてください。

## オプションの制御サービスアドミッション

スタンドアロンの静的トークンリレーは引き続き利用可能です。制御サービス管理下のリレーは次を使用します:

```sh
session-peer relay serve --auth-state /run/session-peer-auth/state.json \
  --auth-issuer https://relay.example.com \
  --auth-replay-state /private/relay-state/spent-tickets.json --bind 127.0.0.1 --port 3769 --seconds 0
```

`--auth-state` と `--accounts` は相互排他です。読み取り専用の状態には、検証用公開鍵と最小限のデバイス所有権/失効レコードが含まれます。エンドポイントの秘密鍵、ログインセッショントークン、および OAuth プロバイダーのシークレットは存在しません。

アドミッションには、短命な ES256 チケットと、登録された P-256 デバイスキーによる署名が必要です。Audience、issuer、generation、owner、receiver、および room がチェックされます。既存の使い捨て WebSocket クッキーを発行する前に、チケットが1回消費されます。状態が欠落または無効な場合は安全側に倒して失敗（fail closed）し、既存の接続は毎秒失効状態を再確認します。制御サービスによる発行と Python CLI はフィクスチャ統合に合格しています。トークン検証テスト単体では、実際のブラウザログインが確立されたことにはなりません。

## ブラウザログイン（統合候補）

```sh
session-peer device login --state /private/device-state --server https://relay.example.com
session-peer device enroll --state /private/device-state --name laptop --operation-id FULL-UUID
session-peer device pair --state /private/device-state --invite /private/invite.json --route relay --login
session-peer list --device DEVICE-ID --device-state /private/device-state --relay-login --output-format json
```

ヘッドレスログインでは `--no-browser` を使用します。表示された URL を別のブラウザで開き、そのユーザーコードを確認してください。プライベートなデバイスコードおよび生成されたセッショントークンは表示されません。ログイン情報は明示的なデバイスディレクトリにプライベートな 0600 ファイルとして保存されます。期限切れのログインは別の明示的なログインを必要とします。コアなローカル/SSH コマンドがログインを開始したり、このサービスにアクセスしたりすることはありません。

制御サービスは GitHub/Google と連携する Better Auth を使用しており、`control/` の下で独立して管理されています。Python クライアントとサービス API は言語間のフィクスチャ統合に合格しています。専用のプロバイダー認証情報は準備されていますが、実環境での OAuth 検証は未完了のままです。単体テストを正常に動作する公開ログインとして報告してはなりません。

制御サービス管理のローテーションでは、`--login` を `device rotate` に追加します。これにより、古い鍵/新しい鍵の証明と安定した操作 ID を使用してステージングされた公開鍵が制御サービスに登録され、独立したピン留めエンドポイントの移行を完了する間、外部アドミッションにその新しい鍵が使用されます。失敗した後は同じ操作 ID を再利用してください。

リレーはクッキーを発行する前に使用済み JWT ID をコミットし、再起動をまたいでこの小さなリプレイファイルを保持します。ペイロードは永続化されません。制御公開状態は60秒ごとに更新され、180秒以内に期限切れになります。欠落、期限切れ、または無効な状態の場合、アドミッションは拒否され、既存の管理対象接続は切断されます。

管理アドミッションはまた、既存のグローバルな10接続制限の範囲内で、1ユーザーあたり8つ、1デバイスあたり4つのオープンなリレー接続に制限します。パブリック状態には永続的に増加するリビジョンが付与されます。リレーは最も高いリビジョンを記憶し、再起動後であっても、ロールバックや同じリビジョンでの競合するコンテンツを拒否します。この最高水位標は使用済みチケットファイルとともに保持され、制御状態の回復中に破棄してはなりません。

オペレーターはサービスアイデンティティとして、リプレイ状態を一度初期化する必要があります:

```sh
session-peer relay init-replay --out /private/relay-state/spent-tickets.json
```

これはファイルのいかなる上書きも拒否します。アドミッションは、この明示的な初期化から少なくとも65秒以降に発行されたチケットのみを受け入れます。`serve` は欠落したリプレイ状態の再作成を拒否します。自動再起動フックに初期化を組み込まないでください。状態が失われた場合は、明示的な復旧の前に制御権限を調整/フェンスしてください。使用済みチケット ID はすぐに期限切れになりますが、同じファイルが制御リビジョンの最高水位標も保持しているため、サービスの存続期間全体にわたって保持される必要があります。

## KR サービスのバックアップと復元ステージング

デプロイされた KR サービスは、暗号化された Restic ジョブの前に `deploy/ops/abruption-kr/session-peer-backup-snapshot.py` を使用します。このヘルパーは連動するスタックを一時的に停止し、トランザクションとして一貫した制御データベース、アドミッション署名鍵、プロバイダー設定、パブリック認証状態、およびリレーリプレイ/最高水位標ファイルを含む root 専用の回復セットを作成します。スナップショットを公開する前にデータベースの整合性と署名鍵の公開 JWK を検証し、その後に以前アクティブだったスタックを復元します。不完全なスナップショットは DR ジョブを中止させます。

Restic のスコープには、イミュータブルな制御およびリレーランタイム、準備完了ヘルパー、インストールされたサービスユニットも含まれます。復旧では、まず分離された root 専用ディレクトリに復元し、スナップショットマニフェスト、ファイルハッシュとモード、SQLite テーブル数、状態/リプレイリビジョン、使用済みエントリ、署名鍵、ランタイムリンクを検証する必要があります。稼働中のサービスに直接上書きしたり、古い制御データベース、署名鍵、またはリプレイ最高水位標を自動的に昇格させたりしないでください。本番環境の置き換えには、依然として停止されたスタックと明示的なロールバック/失効フェンスが必要です。
