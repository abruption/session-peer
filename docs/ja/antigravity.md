# Antigravity CLI アダプター (実験的)

この実験的なオプトインアダプターは、session-peer v0.9.0 で利用可能です。`pipx install session-peer` または `uv tool install session-peer` でインストールしてください。リリースの利用可能性は、長期的な運用安定性を確立するものではありません。これは内部アダプター/トランスポートのリファクタリング（#47）を使用しており、ペアリングされたデバイスへの配信用ターゲット（#69）として承認できます。Antigravity 自体が自動的にインストールされることは決してありません。フィルタなしの一覧取得には、アクティブなブリッジ登録が含まれます。

ユーザーが起動したローカルブリッジと [公式の agentapi インターフェース](https://antigravity.google/docs/sidecars/) を使用して、**既存の TUI** に配信します。Mac および Linux CLI 1.2.4 の実験ではアイドル配信が実証されましたが、CLI サイドカーの自動起動メカニズムは確立されて**いません**。`agy -p` や `--conversation` で別のライターを起動することは配信の代替手段にはなりません。Windows でのブリッジ動作はサポートされていません。他のアダプターは引き続き Windows でも利用可能です。

## 受信側 TUI からの登録

受信側の agy TUI に対し、通常のツールランナー経由でこのコマンドを実行するよう要求します:

```sh
session-peer antigravity-bridge serve --thread FULL-CONVERSATION-UUID
```

TUI を所有するアカウントとして実行してください。他のユーザーが所有するワークスペースディレクトリによって CLI のホームが識別されることはありません。デフォルトのホームは `~/.gemini/antigravity-cli` です。カスタムホームの場合は `--antigravity-home /absolute/path` を使用してください。登録時に、祖先 `agy` プロセス、UID、開始時刻、およびその正確なホームと会話に対して開かれたプレゼンスファイルが検証されます。Linux は `/proc` を使用し、macOS は `ps` と `lsof` を使用します。開かれたプレゼンス FD は同一性の証拠であり、**カーネルロックを保持している証明ではありません**。一致する祖先の登録が複数ある場合、それらから送信者を推測することはありません。

ブリッジは認証済みのツール環境を継承し、`<home>/bin/agentapi send-message` を呼び出します。プロセスの環境変数を抽出したり、トークンをコピーしたりすることは決してありません。無関係な SSH シェルから実行したり、認証情報を捏造したり、ツール権限の拒否をバイパスしたりしないでください。プレーンな SSH プロセスが TUI の代わりにこの登録を作成することはできません。長時間実行コマンドとして起動してください。ready JSON はローカルエンドポイントがリスニング中であることを意味し、モデルが何かを消費したことを意味するわけではありません。

デフォルト: 有効期間 3,600 秒（最大 86,400 秒）、最大 1,000 件の一意なリクエスト（最大 10,000 件）。`--ttl` および `--max-requests` は、これらの明示的な制限値を下げたり上げたりします。デーモン、グローバルサイドカー設定、または自動再起動はインストールされません。

## 検出と送信

```sh
session-peer list --agent antigravity --host ubuntu@worker --json
session-peer send --host ubuntu@worker --to antigravity:FULL-CONVERSATION-UUID \
  --antigravity-home /home/ubuntu/.gemini/antigravity-cli \
  --antigravity-generation GENERATION-FROM-LIST \
  --message 'Please review the proposed change' --json
```

ローカル配信の場合は `--host` を省略します。通常の SSH トランスポートはスタンドアロンのソースを送信先へストリーミングするため、送信のためにリモートにパッケージをインストールする必要はありません。受信側のブリッジはすでに実行されている必要があります。登録されたセッションはフィルタなしの `list` にも表示され、`agent: antigravity`、`antigravityHome`、`ownerPid`、`ownerStart`、`generation`、および `status: registered` が含まれます。このステータスはアイドルを意味するものではありません。検出スコープは `registered_bridges` です。`--all` を指定した場合でも、過去のセッションや未登録の TUI セッションは列挙されません。理由が `no_live_registration` である `not_installed` は、アクティブなブリッジが存在しないことを意味し、agy がアンインストールされた証明ではありません。

`--antigravity-home` は送信先にある既知の登録をフィルタリングします。同じ UUID に対して 2 つのアクティブなホームが存在する場合、フィルタリングしない限り `ambiguous_home` で失敗します。世代の固定により、置き換えられた登録経由での配信が防止されます。`--dry-run` は agentapi を呼び出すことなく登録を検証します。本文は 32 KiB UTF-8 に制限されます。ネイティブの送信者アイデンティティは受信側 TUI の agentapi アイデンティティです。`From:` ヘッダーは説明的なものであり、リモートエージェントの暗号論的な認証ではありません。

## 結果の規約

- `status: submitted`、`ok: true`、`submitted: true` は、agentapi が終了コード 0 で終了したことを意味します。
- `consumptionConfirmed: false` は false のままです。自動化された ACK/待機機能は提供されません。`--wake` はサポートされていません。必要に応じて返信を個別に確認してください。
- タイムアウト、起動失敗、ゼロ以外のネイティブ終了コード、またはブリッジ応答の喪失時は `status: unknown`、`ok: false`、`retryAllowed: false` が返されます。自動的に再送信しないでください。
- リクエスト検証エラーはネイティブの呼び出し前に拒否されます。`reason` と `error` を調査してください。構造化された応答の前のリモートトランスポート障害でも、結果が unknown のままになることがあります。
- `requestId` と `generation` がこの試行を識別します。オプションの `--request-id UUID` には `--antigravity-generation UUID` が必要です。**同一のブリッジ世代**内での同一の ID/本文に対しては、キャッシュされた結果が `duplicateSuppressed: true` とともに返されます。その ID で内容が変更された場合は拒否されます。永続的な送信トレイ、再起動をまたぐリプレイ、厳密に 1 回の保証はありません。unknown を再試行するために ID を変更しないでください。

ブリッジには同一 UID チェック、プライベートな `/tmp/session-peer-agy-UID` ディレクトリ（0700）、登録ファイルおよびソケット（0600）、制限付きフレーム化 JSON 読み取り、および 15 秒のネイティブ呼び出しタイムアウトが備わっています。ネイティブの stdout/stderr は破棄され、エラーにシークレットが含まれることはありません。agentapi に渡されるメッセージ本文はネイティブプロセスの引数であり、十分な権限を持つプロセス検査から見える可能性があります。同じ OS ユーザーとして実行されている他のプログラムは、同一の信頼境界内にあります。

## 停止と再登録

```sh
session-peer antigravity-bridge stop --thread FULL-CONVERSATION-UUID
```

カスタマイズしている場合は、同じホームオプションを指定して受信側のマシン/アカウントで実行してください。停止、TTL、所有者プロセスの終了、SIGINT/SIGTERM/SIGHUP により、ソケットと登録が削除されます。実行中のネイティブリクエストがある場合、15 秒の期限までクリーンアップが遅延する可能性があります。SIGKILL やマシンの障害ではクリーンアップを実行できません。次回の serve は、古いファイルを削除する前に排他ロックを保持し、新しい世代を使用します。スプリットロック競合を防ぐため、小さなロックファイルは意図的に残されます。アクティブなロックファイルをアンリンクしないでください。

TUI の再起動後は、その TUI から明示的に再度登録してください。検出時に所有者が再度チェックされるため、古いパスや再利用された PID だけでは不十分です。権限エラーや検査失敗によってセッションが送信可能になることはありません。`doctor` はアクティブなブリッジが存在しない場合に Antigravity を `disabled` として報告します。このオプション機能によって、正常な Claude/Codex 環境が損なわれることはありません。

MCP には宛先の明示的な `agents: ["antigravity"]` と `send` 権限が必要です。ソースの登録によって送信権限が付与されることはありません。MCP は現在、カスタムの Antigravity ホーム/世代を固定することができません。その制御には CLI を使用してください。複数のホームが存在する場合は曖昧なままであり、フェイルクローズします。Reply-To URI はエージェント/UUID を保持しますが、ホームの固定は保持しません。

## 検証

`python3 -m unittest tests.test_antigravity -v` は、断片化/無効/サイズ超過フレーム、正確なターゲット/世代チェック、PID の再利用、パーミッション、リクエストの競合、タイムアウト、dry-run、SSH 構造化結果、送信者アイデンティティ、および MCP 許可リストをカバーしています。実際の Unix ソケットと子プロセスのフィクスチャにより、モデルの認証情報なしで SIGTERM クリーンアップと古い状態からの再起動がテストされます。実稼働テストの境界と残りの作業については、[開発検証](validation/85-antigravity.md) を参照してください。
