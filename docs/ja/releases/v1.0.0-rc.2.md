# session-peer v1.0.0-rc.2

準備中の候補であり、公開のお知らせではありません。RC2 は RC1 契約を維持して #158 を統合します。明示的なプレリリーステスト以外では、安定版 v0.9.2 を使用してください。

## RC1 以降の変更

- #157: Windows Claude レジストリの peerToken をプロトコルの token に変換します。不正なキーを拒否し、認証後にメッセージを送る順序を維持します。v0.9.2 にも公開済みです。
- #153: ネイティブ Windows Codex writer ロック、一意の所有者、同一ユーザー SID、実行ファイル、プロセス作成時刻を検証します。不明・曖昧な証拠では拒否します。
- #156: Linux から Windows SQLite/WAL を読む代わりに、WSL から運用者指定のネイティブ Python で Windows Codex の検出と送信を実行します。
- #151: 使用不能な SSH python3・Windows Store エイリアスと POSIX 互換リモートシェルの要件を説明します。v0.9.2 にも公開済みの診断であり、ネイティブ Windows SSH シェル対応を追加するものではありません。

## 必須の WSL ポリシー移行

- 既存の Windows Codex バインディングに `codexPython` が必要です。インストール済みのネイティブ Windows Python 3.9+ の `python.exe` を指すマウントされた絶対パスで、Store エイリアスやシンボリックリンクは不可です。[ペアリングガイド](../paired-devices.md)を参照してください。
- 固定の `codexHome` と `codexBin` を維持します。レシーバーは稼働 writer 検査を省略しません。Linux/macOS は両実行ファイルフィールドを省略します。
- デバイス ID、ピン、受領記録、tombstone、replay 状態を保持します。更新中に状態を削除したり結果不明のメッセージを再送したりしないでください。
- ネイティブ Windows のコアと MCP は対応します。レシーバー・リレーは Unix または WSL と Python 3.11+ が必要であり、ネイティブ Windows リレー対応ではありません。

## 公開後のインストール

ペアリングした両エンドポイントで同じパッケージ管理方式と正確なバージョンを使います。既存の管理環境内でアップグレードし、別のインストール管理方式に置き換えないでください。

```bash
# Unix / WSL with relay and MCP
pipx install 'session-peer[relay,mcp]==1.0.0rc2'
# Native Windows core and MCP, without relay
pipx install 'session-peer[mcp]==1.0.0rc2'
```

Python/PyPI バージョンは `1.0.0rc2`、GitHub タグは `v1.0.0-rc.2` です。依存関係なしのコアは Python 3.9+、MCP は Python 3.10+ が必要です。

## 証拠と残りの条件

このバージョン更新前に、ユーザーはネイティブ Windows Codex、公開 Relay → WSL → ネイティブ Codex、パッケージ化された安定版 Claude 修正の正確な ACK を独立確認しました。ネイティブ Windows MCP の一覧・dry-run と SSH 診断も成功しました。これは修正候補の証拠であり、RC2 の全ホスト導入や連続運用観察の成功を意味しません。

RC2 の受け入れ証拠を記録するまで #150 と #151/#153/#156/#157 を開いたままにします。`posted` や `queued` を消費とみなさないでください。独立した ACK がなければ `consumptionConfirmed: false` が正確です。

## 公開後の検証計画

1. 公開された正確なタグ・コミット、wheel・sdist ハッシュ、新規インストールを検証します。GitHub は Latest ではなく prerelease とし、安定版更新は v0.9.2 を選ぶ必要があります。
2. インストールファイルのバックアップと承認済みの一貫した状態スナップショット後、Mac mini、MacBook、quintet-desktop、KR、US に正確な RC2 を導入します。運用 ID と replay 状態を保持し、管理方式を黙って置き換えません。
3. 検出、JSON スキーマ、診断、dry-run、MCP ポリシーを再検証します。Windows Claude/Codex と WSL→ネイティブ Codex を新しい相関トークンと独立した実 ACK で確認し、Mac・サーバー基本経路も検証します。SSH 設定を変更せず、非対応のネイティブ SSH 境界の案内を確認します。
4. レシーバー転送コードの変更により #150 の全ホスト 4 時間観察を繰り返します。毎分の正常性、5 分ごとの直接・リレープローブ、T0/T2h/T4h の独立 ACK、T2h の調整済みリレー再起動 1 回を実施します。再接続、失効・復旧、重複・競合 ID、unknown 結果の保持を検証します。RC1 の証拠は RC2 を代替しません。
5. 環境、正確な成果物、秘匿化した証拠を各 issue に記録します。説明不能な失敗、ACK 欠落、前提不足は昇格を阻止します。PR マージや PyPI 公開だけで RC2 マイルストーンを閉じません。

## リリース境界

- 準備はタグ、公開、全ホスト更新、運用再起動を承認しません。別途承認後に実行します。
- Antigravity は実験段階です。ホスト Relay・OAuth の健全性はパッケージ公開と独立しています。
- ACK を強制するために受信権限を変更したり、曖昧な送信を再試行したり、認証情報を公開したり、ピア要求を直接のユーザー承認とみなしたりしないでください。
