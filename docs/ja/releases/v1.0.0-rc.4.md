# session-peer v1.0.0-rc.4

RC4 は部分公開された RC3 を新しいバージョンで修正公開します。PyPI は RC3 の wheel を受理しましたが、sdist のアップロードは HTTP 502 の反復により失敗しました。RC3 は安定版への昇格に使用できません。RC4 はパッケージのバージョンとリリース文書のみを変更し、ランタイムの動作はレビュー済みの #162 と #168 の実装と同じです。明示的にプレリリースを試す場合を除き、安定版ユーザーは v0.9.2 を維持してください。

## RC2 以降の変更

- #162 は fail-closed のルート契約を維持しつつ、試行ごとの匿名化された段階と任意の診断イベントを追加します。control/admission の設定再試行はアプリケーション送信前に限られ、メッセージは再送されません。
- #168 は正常な idle 満了後の受信側再接続遅延を 0.5 秒に保ち、Relay レグに 10/10 秒 ping を使用し、receiverRoleBusy と clientRoleBusy のカウンターを追加します。
- #163 のオフライン再現が示すのは経路停滞の増幅低減であり、経路自体の修復や #161 解決の証拠ではありません。

## 完全公開後のインストール

両方のペアリング済み端末で既存のパッケージマネージャーを使い、正確な候補を導入してください。別のマネージャーに切り替えたり、RC3 の不完全なファイル群からインストールしたりしないでください。

```bash
# Unix / WSL with relay and MCP
pipx install 'session-peer[relay,mcp]==1.0.0rc4'
# Native Windows core and MCP, without relay
pipx install 'session-peer[mcp]==1.0.0rc4'
```

Python/PyPI バージョンは 1.0.0rc4、GitHub タグは v1.0.0-rc.4 です。コアは Python 3.9+、MCP は 3.10+、受信側/Relay ランタイムは Unix または WSL の 3.11+ が必要です。

## 証拠と残る条件

RC2 の 4 時間キャンペーンは完了記録なしで 172 分に終了しました。正確に完全公開された RC4 が 5 ホスト検証に合格するまで、#161、#163、#164 を開いたままにしてください。posted または queued は消費された ACK ではありません。独立した観測がない場合は `consumptionConfirmed: false` が正しい結果です。

## 公開後の検証計画

1. 公開されたタグとコミット、PyPI の両ファイルのハッシュ、wheel と sdist の新規インストール、プレリリース状態、安定版 v0.9.2 の latest 状態を確認します。
2. Mac mini、MacBook、quintet-desktop（ネイティブと WSL）、KR、US に正確な RC4 をインストールする前に、インストールファイルと承認済みの一貫した状態スナップショットをバックアップします。デバイス ID、ポリシー、リプレイ防止状態を維持します。
3. 独立したプロセスで complete または aborted を記録する #164 の 5 ホスト 4 時間キャンペーンを実行します。毎分の health、受信側ごとに 5 分以上離した probe、診断イベント、毎分の receiverRoleBusy/clientRoleBusy、T0/T2h/T4h の独立 ACK、T2h の Relay 再起動と 60 秒以内の回復目標を含めます。
4. すべての失敗を段階別に分類します。説明できない失敗、欠落した ACK、不完全な実行は昇格を妨げます。公開や PR のマージだけでマイルストーンを閉じないでください。

## リリース境界

準備だけでは公開や全端末の検証は完了しません。Antigravity は実験的であり、ホストされた Relay/OAuth の健全性はパッケージ提供とは別です。結果不明のメッセージを再送したり、ACK を強制するために受信権限を変更したりしないでください。
