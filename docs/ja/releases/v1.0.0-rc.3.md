# session-peer v1.0.0-rc.3

準備中の候補であり、公開のお知らせではありません。RC3 は RC2 契約を維持し、#161 で追跡している断続的な公開リレー経路の失敗を対象とします。明示的なプレリリーステスト以外では、安定版 v0.9.2 を使用してください。

## RC2 以降の変更

- #162: 経路の失敗は `no_authenticated_route`、`retryAllowed: false`、`consumptionConfirmed: false` を維持しつつ、試行ごとにサニタイズされた段階・理由・経過時間と WebSocket 切断コード・発生元を報告します。control と admission の設定タイムアウトは、アプリケーション送信前に新しい admission で 1 回だけ再試行し、エージェントメッセージは決して再送しません。
- #162: オプトインの `--diagnostic-events` はメタデータのみの受信側ライフサイクルイベントとリレールームイベントを出力し、リレー指標にルーム・attach・期限切れカウンターを追加します。診断は既定で無効です。
- #168: 1 秒以上開いていた待機ルームがリレーにより正常に閉じられた場合、受信側はバックオフを増やさず 0.5 秒後に再接続します。リレーレグは 10 秒の WebSocket ping 間隔・タイムアウトを使うため、停止したレグを約 40 秒ではなく約 20 秒で検出します。
- #168: リレー指標に、拒否された重複レグを数える `receiverRoleBusy` と `clientRoleBusy` を追加します。
- #163 のオフラインのループバック再現で、これらの変更が停止した経路を増幅する再接続の空白を減らすことを確認しました。停止したネットワーク経路を修復するものではなく、#161 が解決した証拠でもありません。

## アップグレードの注意

- スキーマ・状態・ポリシーの移行はありません。デバイス ID、ピン、受領記録、トゥームストーン、再送防止状態を保持し、状態を削除したり結果不明のメッセージを再送したりしないでください。
- リレーとペアリング済みの両エンドポイントを同じバージョンにアップグレードしてください。新しい指標とイベントは追加型です。[ペアリングデバイスガイド](../paired-devices.md)を参照してください。
- ネイティブ Windows のコアと MCP は引き続きサポートされます。受信側/リレーのランタイムには Unix または WSL と Python 3.11+ が必要です。

## 公開後のインストール

ペアリングされた両エンドポイントで同じパッケージマネージャーと正確なバージョンを使用してください。既存の管理対象インストールは既存環境内でアップグレードし、別のインストールマネージャーに置き換えないでください。

```bash
# Unix / WSL with relay and MCP
pipx install 'session-peer[relay,mcp]==1.0.0rc3'
# Native Windows core and MCP, without relay
pipx install 'session-peer[mcp]==1.0.0rc3'
```

Python/PyPI のバージョンは `1.0.0rc3`、GitHub タグは `v1.0.0-rc.3` です。依存関係のないコアには Python 3.9+、MCP には Python 3.10+ が必要です。

## 証拠と残りの条件

RC2 の 4 時間観察は完了記録なしに 172 分で停止し、公開リレーの失敗を記録したため、合格した soak ではありません。オフライン再現はメカニズムを示すものであり、実際の障害原因を確定しません。

公開された正確な RC3 が 5 ホストの観察に合格するまで、#161、#163、#164 を開いたままにしてください。`posted` や `queued` を消費と見なさないでください。独立して観測された ACK がなければ、`consumptionConfirmed: false` がそのまま事実です。

## 公開後の検証計画

1. 公開された正確なタグ・コミット、wheel・sdist のハッシュ、新規インストールを検証します。GitHub は Latest ではなくプレリリースのままにし、安定版のアップグレードでは引き続き v0.9.2 が選択される必要があります。
2. Mac mini、MacBook、quintet-desktop(ネイティブと WSL)、KR、US に正確な RC3 をインストールする前に、インストールファイルをバックアップし、承認済みの一貫した状態スナップショットを使用します。本番の ID と再送防止状態を保持し、インストールマネージャーを黙って置き換えないでください。
3. 常に `complete` または `aborted` を記録する独立した監督プロセスで、5 ホストの 4 時間観察 (#164) を実施します。毎分のヘルスチェック、同じ受信側への probe 間隔を 5 分以上空けた直接・リレー probe、`--diagnostic-events` の有効化、毎分の `receiverRoleBusy` と `clientRoleBusy` の記録、T0/T2h/T4h の新しいトークンによる独立 ACK、60 秒以内の回復を目標とした T2h のリレー再起動 1 回を含みます。
4. 失敗は診断段階ごとに記録します。説明のつかない失敗、欠落した ACK、未完了の観察は昇格を妨げます。PR のマージや PyPI 公開だけを理由に RC3 マイルストーンを閉じないでください。

## リリース境界

- 準備はタグ、公開、機器の置き換え、本番の再起動を承認するものではありません。承認を得て個別に実行してください。
- Antigravity は引き続き実験段階です。ホストされたリレー/OAuth の健全性はパッケージ公開とは独立しています。
- ACK を得るために受信権限を変更したり、曖昧な送信を再試行したり、レポートで資格情報を公開したり、ピアの依頼をユーザーの直接承認と見なしたりしないでください。
