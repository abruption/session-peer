# session-peer v1.0.2

v1.0.1 に続く安定性重視のメンテナンスリリースです。ローカル/SSH コアは Python 3.9+ で外部依存なしを維持します。Relay と MCP は任意で、Antigravity ブリッジは実験段階です。

## 変更点

- Control は拒否・失敗した変更後も health と公開状態の整合性を維持します(#200)。コミット前にリーダーの 1 MiB UTF-8 制限を検査し、失効記録を削りません(#208)。
- Control はレート制限用にループバックのリバースプロキシが渡すクライアント識別情報を認証できます。任意の転送ヘッダーは信頼しません(#202)。
- 復旧では完了済みジャーナルを配信の証拠とせず、不明なネイティブ結果を未解決として保持します(#201)。承認スキーマ v2 は `peerGeneration` を署名対象にして鍵ローテーション世代を保持します(#203)。
- standalone インストーラーはダウンロードと CLI 検証後にランタイムを原子的に置き換えます。ダウンロード・検証失敗時は既存のインストールを保持します(#204)。
- 明示的な Codex wake と MCP CLI の終了処理は、TERM に抵抗する子孫も含め、所有する POSIX プロセスグループを回収します(#205, #206)。
- SSH はエンコードと封筒のサイズを含むシェル引用済み UTF-8 コマンドを検査し、上限超過を SSH 起動前に拒否します(#207)。
- SQLite バックアップ fixture は接続を明示的に閉じます(#209)。Relay 設定失敗では許可された理由に基づく案内を返し、依存関係の導入・ログイン・ペアリング・再送を自動実行しません(#210)。
- 互換スキルのスナップショットを v0.3.1 に同期し(#199)、固定した GitHub Actions を更新しました。別途導入したスキルは元の更新管理を維持します。

## インストールと更新の境界

既存のインストール管理ツールを使い、別の導入方法に無断で置き換えないでください。

```bash
pipx upgrade session-peer
# New Unix / WSL installation with optional Relay and MCP:
pipx install 'session-peer[relay,mcp]==1.0.2'
```

コアは Python 3.9+、MCP は 3.10+、Relay 受信側/サーバーは Unix または WSL の Python 3.11+ が必要です。サービス管理下の macOS/Linux 受信側では、サービス PATH の Codex 実行ファイルか運用者管理の `codexBin` 設定が引き続き必要です。送信前に `--dry-run` で対象を確認してください。

- v2 承認を生成する前に復旧をコミットするデバイスを更新してください。旧版は v1 のみ受け入れます。保存した鍵の世代が既知なら旧承認も使えますが、ローテーション世代を推測しません。有効化前に既存の復旧計画を保存した受領記録と照合してください。再開時に過去の計画は書き換えません。
- プロキシ識別情報の認証には `SESSION_PEER_TRUSTED_PROXY_TOKEN_FILE` と、両方の専用ヘッダーを上書きするプロキシの別途設定が必要です。標準はソケットアドレスによるレート制限です。パッケージ導入はプロキシ設定を変更せず、任意の CDN ヘッダーを信頼しません。
- 既に上限を超えた Control DB は容量を安全に解決するまで unhealthy のままです。新しい制限は履歴を削除しません。Control の配備は Python CLI の導入と別です。
- 原子的置換はランタイムファイルだけで、全ファイルのトランザクションや後続のスキル管理失敗のロールバックではありません。POSIX 終了処理は所有グループを脱出したプロセスや SSH のリモートプロセスを含まず、Windows MCP は直接の子だけを終了します。

## 検証と既知の制限

準備ゲートには回帰テスト、文書・翻訳検査、生成ソース検査、アーカイブ検査、再現可能なビルド、クリーンな wheel/sdist インストールが含まれます。新たな実環境 4 時間キャンペーンやホスト型 Relay/OAuth の可用性保証ではありません。過去の RC4 証拠は v1.0.0 のもので、このメンテナンス版の検証に読み替えません。

#161 は未解決です。公開経路の断続的な停滞の根因と責任主体は未確定で、この版がネットワーク経路を修復したとは主張しません。`posted`、`queued`、`submitted` は提出の証拠であり、消費や ACK ではありません。不明な結果を自動再送してはいけません。パッケージ公開、機器への導入、運用再起動は別の操作です。
