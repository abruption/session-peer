# Cloudflare 背後のネイティブクライアント (RC 検証)

リレーのブラウザ UI とネイティブ API には異なるクライアントが存在します。ブラウザの OAuth コールバックや公開ヘルスチェック GET が成功したとしても、デバイスコードの POST や認証済み WebSocket 接続が機能することの証明にはなりません。

KR パイロットにおいて、ネイティブのデバイスコードリクエストが HTTP 403 / Cloudflare 1010 (`browser_signature_banned`) を返しました。対応する Cloudflare セキュリティイベントでは、`source=bic`、`ruleId=bic`、`action=block` が特定されました。これにより、そのリクエストに対して Browser Integrity Check が原因であることが特定され、Bot Fight Mode が原因ではないことが判明しました。

## ネイティブ POST 例外ベースライン

オーナーはまずデバイスコード/トークンのパスを承認し、続いて 3 つの登録/許可 (admission) POST パスを明示的に承認しました。これは単一の Configuration Rule として維持され、`http_config_settings` 内で `action=set_config` および `action_parameters={"bic":false}` が設定されています。その式は以下のとおりです:

```text
(http.host eq "relay.abruption.dev" and ssl and http.request.method eq "POST" and http.request.uri.path in {"/api/auth/device/code" "/api/auth/device/token" "/api/relay/challenge" "/api/relay/devices" "/api/relay/admission"} and http.request.uri.query eq "")
```

これにより、クエリのない 5 つの HTTPS POST エンドポイントに対してのみ BIC が無効化されます。ゾーン全体の BIC 設定、マネージド WAF、Bot Fight Mode、DDoS 保護、セキュリティレベル、既存のレート制限ルール、オリジンインプレス制限は変更されません。既存の Cloudflare レート制限ルールは別のサービスを保護するものであり、リレー固有のレート保護として説明してはなりません。Control 自体のリクエスト制限、固定クライアント ID、コードの有効期限/ポーリング制限、明示的な公開サインアップ切り替えまたはアカウント許可リスト、および明示的なブラウザ承認は引き続き適用されます。このルールに一致しても認証は一切付与されません。

設定は明示的な承認の後に適用されました。v2 ルールの Cloudflare Trace は、意図した 5 つのパスすべてに一致し、他のメソッド/ホスト、クエリ、末尾のスラッシュ、平文 HTTP、ブラウザの承認/取り消し、操作ルックアップ、リレーセッション/WebSocket エンドポイントを含む他の 10 のケースを除外しました。第 1 段階では、実際のネイティブコード発行、ブラウザ承認、トークンポーリングも通過しました。Trace は設定の検証であり、ダウンストリームのネイティブ配信が成功した証拠ではありません。

## 変更とロールバック

このようなルールを別のデプロイに適用する前に、既存の設定フェーズを確認し、他のルールを保持してください。既存のルールセットを上記の例で置き換えたり、ゾーン全体で BIC を無効化したりしないでください。新しいルール ID/バージョンを記録し、保存された式を再確認し、対象となるケースおよび除外されるケースを確認してください。

同時並行の設定変更を保持しながら、追加されたルールのみを元に戻してください (その ID で無効化/削除)。エッジルールのロールバックの一環として、アプリケーションデータベース、キー、レシート、またはリプレイ状態を復元しないでください。

POST 専用のベースラインは、操作ルックアップやリレーセッション/WebSocket GET ルートをカバーしていません。その後に承認された操作ルックアップの適用範囲については以下で説明します。リレーセッション/WebSocket GET には依然として BIC 例外がありません。ブラウザのユーザーエージェントに偽装したり、ブラウザのクッキーを CLI に転送したり、明示的な再試行不能ブロックに対して再試行を繰り返したりしないでください。デバイスコード、トークン、シークレットをログやレポートに含めないでください。

## 承認された操作レシートのルックアップ

オーナーはその後、ネイティブのレシートルックアップにおける 403 の解決を承認しました。新たなネイティブルックアップはエラー 1010 を返しました。GraphQL 診断 API が予算を使い果たしたため、正確な過去のセキュリティイベントを読み取ることができませんでした。BIC のみの変更により、登録を繰り返すことなく、まず単一の受信者レシート URL が復元されました。その限定的な成功実験では、他の ID は解決されませんでした。

同一ルールのバージョン 4 は、現在、リレーホスト上で **クエリのない HTTPS GET** に追加で一致し、`/api/relay/operations/` の後に正規の小文字 UUIDv4 が続くパスを対象とします。その 58 バイトのパス、16 進文字、ハイフンの位置、バージョン、バリアントは、このデプロイでサポートされている `starts_with`、`len`、`substring`、および文字単位の比較を使用してチェックされます。有料の正規表現機能やプランのアップグレードは使用されませんでした。サポートされていない代替式は、アクティブな設定を変更することなく拒否されました。これは運用レシピではありません。

Trace は、既存の操作 ID と不正な形式の ID、大文字、誤ったバージョン/バリアント、末尾のスラッシュ、クエリ、メソッド/ホスト/プロトコル、および無関係な API の除外を含む 21 のケースを通過しました。その後、元々登録されていた両方のデバイスが、新たな登録を行うことなく CLI exit 0 でコミット済みレシートを照合 (reconcile) しました。別の認証済みオーナーおよび存在しない正規操作 ID は、アプリケーションから 404 を受け取りました。この例外は BIC のみをバイパスし、所有権を付与したり API 認証をバイパスしたりすることはありません。

この設定を再利用する前に、ターゲットゾーン/フェーズで正確な式を検証し、そのほかのルールを保持してください。パイロットのサニタイズされた式、API 結果、およびロールバック diff は、[RC validation](validation/69-rc.md) で引用されている運用エビデンスディレクトリ内の `DYNAMIC-RECEIPT-BIC-RESULT.md` に保持されています。

参照: [Cloudflare error 1010](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/) および [Browser Integrity Check](https://developers.cloudflare.com/waf/tools/browser-integrity-check/)。
