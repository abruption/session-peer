# 初回 Google アカウントのディスカバリ（開発）

このオプトインのオペレーター手順は、リレーの許可リストに ID を追加する前に、検証済みの Google アカウント ID を取得します。公開サインアップの有効化、セッションの付与、またはメールアドレスの一致による Google と GitHub アカウントの連携は行いません。実際のプロバイダー検証は引き続き RC ゲートであり、モックされたプロバイダーテストは別個のエビデンスです。

専用の Google Web OAuth クライアントと、正確に設定されたコールバックを使用してください: `https://relay.example.com/api/auth/callback/google`。プライベートリレーの準備中は、アプリケーションを Testing 状態に維持し、Google テストユーザーを制限してください。既存の保護されたファイル/systemd クレデンシャルパスを通じてシークレットを提供してください。

初回の Google ログインの前に、これら 2 つの**一時的**な制御設定を行ってください:

```text
SESSION_PEER_GOOGLE_DISCOVERY_EMAIL=the-explicitly-approved-account@example.com
SESSION_PEER_GOOGLE_DISCOVERY_UNTIL=REPLACE_WITH_UNIX_SECONDS_WITHIN_30_MINUTES
```

両方の設定、有効化された Google プロバイダー、および最大 30 分以内の将来の期限が必要です。このモードが有効になっている間は、期限後も含めて新しい Google ログインがすべて防止されます。通常の Google 認証を再開するには、両方の設定を削除してください。既存のアカウント許可リストは緩和されません。

1. これらの設定と通常の保護された状態で、レビュー済みの制御候補を開始します。承認されたユーザーのブラウザで Google サインインフローを開きます。
2. Better Auth は通常の認可コード、state、および PKCE の交換を実行します。ラッパーは、Better Auth の固定ベリファイアを通じて、返された Google ID トークンを検証します: 署名、発行者、クライアントオーディエンス、有効期限、および最大トークン有効期間。ライブラリが期待される nonce を提供する場合、その nonce もチェックされます。プロバイダーフローから nonce が提供されなかった場合に、nonce が発行されたと主張することはありません。
3. 正確に期待されるメールアドレスと `email_verified=true` を持つ実際の Google コールバックのみが `<SESSION_PEER_CONTROL_DATA>/google-account-discovery.json` を作成できます。このプライベートファイルには、検証済みのサブジェクト、期待されるメールアドレス、検証時刻、発行者、および公開クライアント ID が含まれます。認可コードやプロバイダー/セッショントークンは含まれません。
4. コールバックは、アカウント連携またはプロビジョニング前のログインを意図的に拒否します。ディスカバリ期間内に、同じ保護された設定を持つ同じサービス ID として `node dist/server/confirm-google-discovery.js` を実行し、信頼できるオペレーターパス経由でディスカバリレコードを確認します。これにより、期待されるアカウント/クライアントとプライベートファイルがチェックされ、ファイルとディレクトリが同期された後、`persistenceConfirmed: true` が返されます。その正確な `accountId` を `SESSION_PEER_ALLOWED_ACCOUNTS` に `google` エントリとして追加し、両方のディスカバリ設定を削除します。他の承認済みアカウントエントリは保持してください。
5. レビュー済みのサービス手順に従って再起動し、別途通常の Google ログインおよび CLI デバイス承認テストを実行します。ディスカバリコールバック自体はログインの成功ではありませんでした。

ディスカバリファイルは非公開で準備および同期された後、プライベートな 0700 ディレクトリ内でモード 0600 の上書き不可のハードリンクによって 1 回だけ公開されます。再試行、異なるサブジェクト、期限切れの期間、または書き込みの失敗によって、これが置き換えられたりアクセス権が付与されたりすることはありません。ファイルが存在することだけでは永続性は証明されません。公開後にディレクトリの同期が失敗した可能性があります。明示的な確認ステップでは、検証済みレコードの変更やログインの許可を行うことなく、同期を再試行します。失敗した場合は、許可リストを変更せず、まずストレージを診断してください。オペレーターがディスカバリを再実行する必要がある場合は、まず以前の結果を検査して明示的にアーカイブしてください。再起動時に自動的に削除しないでください。

`accountLinking=false` が引き続き有効です。メールアドレスがすでに GitHub で作成されたユーザーに属している Google アカウントは、`account-not-linked` で拒否される場合があります。ディスカバリはそのチェックの前でも機能します。自動連携は承認されません。個別の変更で明示的なアカウント連携ポリシーが追加されない限り、個別の承認された所有者または隔離されたテスト状態で別々のプロバイダーを検証してください。
