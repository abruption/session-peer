# 明示的なCodexの起動

## 連鎖する wake の制限

CLI と MCP は投入前に `SESSION_PEER_WAKE_DEPTH` と `SESSION_PEER_WAKE_ORIGIN` を読み、各 wake で段数を一つ増やして発生元 UUID を保持します。既定は 3 段で、超過時は何も投入せず `wake_depth_exceeded` を返します。運用者は `--wake-max-depth` または `SESSION_PEER_WAKE_MAX_DEPTH` で 0–16 の範囲で明示的に変更できます。0 は wake を無効にします。不正または不完全な文脈は投入前に `invalid_wake_context` で拒否します。通常の送信は従来どおりキューへの投入のみです。

所有する app-server に増加後の文脈を渡します。SSH は環境転送に頼らず、型を検証した文脈を渡します。宛先は受け取った限度を下げられますが上げられません。複数宛先は発生元を共有しますが予算は独立です。MCP は起動時の環境を読み、呼び出したスレッドを認証しません。Wake はキューメッセージに診断表示を付け、投入後または正常な dry-run 後に `depth`、`origin`、`maxDepth` を含む `wakeProvenance` を追加します。表示も 32 KiB 制限に含まれます。表示や本文は権限を与えず、段数を復元するためにキュー・履歴・会話本文を読みません。

非アクティブ対象の起動は正規化されたホームとスレッドごとに 60 秒間で 3 回が既定です。運用者が管理する `SESSION_PEER_WAKE_TARGET_RATE` は 0–16 を受け付け、0 は非アクティブ対象の起動を無効にします。予約は既存の wake ロック下に保存します。`wake_rate_exceeded` は投入前に拒否し、読めない・大きすぎる・不正な状態は `wake_rate_state_invalid` で拒否します。失敗や中断でも予約は残り、時計が戻っても保守的に保持します。Dry-run とアクティブだと確認したライターは起動枠を消費しません。既存の `wake_in_progress` と `already_active` は維持します。対象やホストの予算は独立し、運用者や同一ユーザーのプロセスは協調的な状態を初期化できるため、全体の費用上限や呼び出し元の認証ではありません。

固定した Codex 0.154.0 ソースでは、シェルの `inherit="all"` は除外規則や `include_only` がなければ変数を保持し、`inherit="core"` と `inherit="none"` は明示的な設定がなければ除去します。既定の秘密名フィルターには該当しません。stdio MCP の既定の許可リストには含まれず、新しい MCP プロセスには `env_vars` 転送が必要です。既存・共有 MCP プロセスは後の呼び出し元の環境を受け取りません。静的な `env` 設定は文脈を初期化したり競合させたりします。文脈が失われると新しいローカル発生元になるため全体の段数上限は保証できず、ローカル起動制限は別の補助策です。承認・プロファイル・ネイティブ環境ポリシーは自動変更しません。

隔離した子プロセスのテストは上流ソースの規則を模倣し、CLI・MCP・SSH の文脈と app-server 代替プロセスの環境を検証します。認証済みのネイティブシェル・MCP クライアント・モデルターンは実行せず、0.154.0 以外の wake サポートの根拠ではありません。出典: [固定したシェルポリシー](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/protocol/src/shell_environment.rs)、[固定した MCP 環境](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/rmcp-client/src/utils.rs)、[現在の設定資料](https://developers.openai.com/codex/config-reference/)。

`session-peer send --to codex:<uuid> --wake --wake-timeout 30 "message"`

通常のsendはキュー送信のみのままです。Wakeは、対象の既存の設定のもとでモデルの使用量を発生させ、セッション履歴やプロジェクトファイルを変更する可能性があります。これにはmacOS/Linuxおよびライフサイクルとネイティブライターの排他制御がテストされたバージョンである**Codex CLI 0.154.0**が必要です。他のバージョンは、個別に検証されるまで安全側に倒して失敗します。このバージョン境界はwakeにのみ適用されます。

オペレーターは通常どおり `--codex-home` およびSSHの `--host` を選択できます。元の作業ディレクトリは、そのホームに保存されたスレッドレコードから取得されます。存在しない、アーカイブされた、未初期化の、所有者不明の、および利用不可能なディレクトリのターゲットは、エンキュー前に拒否されます。state/queue DBが直接変更されることはありません。session-peerのガードは、同じ正規ホームおよびUUIDに対するwakeリクエストをシリアル化します。ネイティブCodexのライターロックも、無関係な同時の再開から保護します。

## ネイティブのライフサイクル

`codex exec resume UUID` は0.154.0においてプロンプトを必要とし、入力を追加せずにキューをアクティブ化することはできません。Wakeは代わりにネイティブの `codex app-server` を起動し、そのstdioプロトコルを初期化してから、正確なUUIDと元のcwdを指定して `thread/resume` を呼び出します。Resume自体が保留中のキューメッセージを消費します。session-peerが `turn/start` を呼び出したり、メッセージをプロンプトにコピーしたり、スレッドをフォークしたり、ライターのロックを解除したり、信頼/サンドボックス/承認設定を変更したりすることはありません。インタラクティブな承認リクエストは明示的に失敗します。app-server APIは実験的であり、別のCLIバージョンをサポートするには再検証が必要です。

すでにアクティブなライターが存在する場合、1つのキュー送信を受け取り、2つ目のプロセスが起動されることはありません。非アクティブな対象に対しては、wakeは期限内（デフォルト30秒、範囲1〜60秒）に1回のネイティブターンの完了を待ちます。その後、自身が所有するプロセスグループを終了します。これは永続的なバックグラウンドワーカーや、キュー全体を処理し切る約束では**ありません**。長時間実行されるターンはタイムアウト時に中断される可能性があり、部分的な作業が残る場合があります。既存のアクティブなプロセスが終了されることは決してありません。

同じライフサイクルとタイムアウトがSSH接続先でも実行されます。接続の切断は不達を証明するものではありません。呼び出し元が切断された場合でも、リモートのwakeには独自の制限されたライフタイムがあります。キャンセルでは、所有するプロセスの正常終了を試み、その後強制クリーンアップを行います。自動再送は発生しません。

## 結果

既存の送信フィールドは維持されます: `submitted`、`queueId`（ネイティブキューが返した場合）、`codexHome`、`status`、および `consumptionConfirmed`。独立した `wake` オブジェクトには、`status`、`reason`、および解決された場合は `cwd` が含まれます。

- `validated`: ドライランのみ。キューへの追加や起動は行われませんでした。
- `already_active`: メッセージがキューに追加されました。既存のライターは実行されたままです。
- `completed`: ネイティブの再開ターンが完了しました。
- `refused`: 安全性/事前確認の要件が満たされませんでした。
- `failed`: ネイティブトランスポート、再開、承認、またはターンの失敗。
- `timed_out`: 所有するアクティベーションが期限を超過し、クリーンアップが試行されました。
- `unknown`: 中断された、または曖昧なアクティベーション結果。

送信が成功してもwakeが失敗することがあります。その場合、CLIの終了コードは0以外になり、JSONにはキューID、`submitted: true`、および失敗が保持されます。**自動的に再送しないでください。** `completed` は特定のキュー項目が受信された証拠ではありません。`consumptionConfirmed` はfalseのままです。以前にキューに入れられた項目や、別の同時送信が完了したターンである可能性があります。

MCPの場合、送信先のケーパビリティに `send` と `wake` の両方を追加し、`send_message(..., wake=true, wake_timeout=30)` を呼び出します。送信権限だけではwakeは許可されません。クライアントのMCPタイムアウトは、キュー/SSH/wake全体のバジェットを超える値（たとえば150秒）に設定してください。そうしないと、クライアントのタイムアウトによって送信結果が見えなくなる可能性があります。

## 検証の証拠

CLI 0.154.0を搭載したmac-mini-m4上で、分離されたテストスレッドが初期化、停止、キューイングされ、新しいプロンプトなしでapp-server経由で再開されました。ネイティブのturn-start/turn-completeイベントが観測されました。最初のプロセスが同じUUIDを保持している間に2回目のapp-server再開を試行したところ、`already has an active writer` で失敗しました。その後、実装されたCLIは別の制御されたメッセージに対して `submitted: true`、キューID、および `wake.status: completed` を返しました。プロジェクトの信頼や承認バイパスのフラグは使用されませんでした。

自動テストでは、フィクスチャSQLiteデータベース、実際の勧告ロック、およびネイティブプロセスの代役を使用します。非アクティブ/アクティブ/アーカイブ済み/存在しないターゲット、デフォルトのキュー送信のみの動作、期限および承認の失敗、プロセスクリーンアップ、同時実行ガードの拒否、中断された送信、リモートの部分的な結果の保持、および個別のMCP権限をカバーしています。ライブのモデル/SSHチェックは手動です。パブリックCIがモデルの認証情報を受け取ることはありません。

その後、実際のCodex 0.154.0 MCPクライアントが、ローカルのlist/send/wakeおよびmac-mini → macbookのlist/send/wakeをリモートのOrcaカスタムホームを使用して完了しました。リモートのデフォルトホームは認証が失効していました。そのキュー送信と失敗したネイティブターンは、認証の変更や再送を行うことなく、部分的な失敗として保持されました。ローカルおよびKR SSHのClaudeプロトコルテスト受信箱も、実際のCodex MCPクライアントからそれぞれ1つのメッセージを受信しました。これらは専用のプロトコルフィクスチャであり、本番のClaudeの会話ではありません。

初期の非対話型Codexテストでは、予想どおり既存の承認ポリシーに基づき書き込みツールが拒否されました。成功したテストでは、テストクライアントの `mcp_servers.session_peer.tools.send_message.approval_mode="approve"` を明示的に設定し、サーバーポリシーでテスト接続先のみを許可しました。出荷されるプラグインにはこの承認オーバーライドは設定されません。プラグインマーケットプレイスへの登録とインストールは、使い捨てのCODEX_HOMEで検証されました。本番のプラグイン設定には手を加えていません。ライブwakeはmacOSでテストされました。Linuxのプロセス/ロック動作はCIフィクスチャでカバーされており、認証情報を使用したモデルの実行ではありません。

macOS/Linux の後処理はリーダーの回収前に所有プロセスグループへ TERM、続いて KILL を送り、TERM を無視する子も終了します。回収後のグループ ID は再利用しません。別セッションへ離脱したプロセスとリモートプロセスは対象外で、送信済み要求を撤回しません。
