## Candidate scope

- #390 / #389 adds MCP SDK compatibility while retaining stable SDK 1.x from 1.30 and admitting stable SDK 2.x from 2.3. The extra uses `mcp>=1.30,<3,!=2.0.*,!=2.1.*,!=2.2.*`; SDK 2.0–2.2, prereleases and development releases remain excluded. SDK 2.3+ uses `MCPServer(subscriptions=False)` and adds no subscription/listen or status/wait interface. The six public tools, project result payload schema version 1, policy versions 1/2, permissions, host approvals, unknown-outcome handling and no-automatic-retry rule are unchanged. SDK 2 Python attributes and camelCase wire aliases are adapted without claiming byte-identical SDK-framework envelopes across protocol versions.
- Dependency maintenance covers #386 GitHub Actions updates, #383 Hatchling 1.33.0, #385 Vitest 5.1.0 and #382 Vite 8.3.6 with @rolldown/pluginutils 1.0.1. These build/CI/development tools are distinct from the dependency-free core CLI and from a running service's environment.
- #379 updates only the test dependency Paramiko 5.1.0 and its matching test assertion. Paramiko remains a test-only fixture dependency; production SSH behavior is unchanged.
- #381 updates Better Auth/core 1.7.18, jose 6.2.15, React/React DOM 19.3.1 and tsx 4.23.15, with dependency-baseline and existing core-contract checks. Application session-policy and runtime authentication code are unchanged; upstream dependency changes are not a claim of verified real OAuth flows or compatibility with an existing production database.

## Compatibility and validation boundaries

Core Python 3.9, optional MCP Python 3.10 and Relay Python 3.11 floors are unchanged. Node's engine remains `^22.13.0 || ^24.0.0`, `@types/node` remains 24 and `better-sqlite3` remains 12.6.2. Control remains private version 0.1.0, outside the Python wheel/sdist; service deployment is separate.

Build-interpreter boundary: the published metadata for [Hatchling 1.32.4](https://pypi.org/pypi/hatchling/1.32.4/json) and [Hatchling 1.33.0](https://pypi.org/pypi/hatchling/1.33.0/json) both require Python 3.10+. This is an existing build-tool requirement, not a new core-runtime floor. Python 3.9 core installations use the universal-wheel or standalone path; a direct sdist build requires a Python 3.10+ build interpreter. This preparation does not claim a tested Python 3.9 sdist build.

The MCP candidate configures four profiles (`minimum`, `latest1`, `minimum2`, `latest2`) on macOS/Linux with Python 3.10/3.13/3.14, for 24 CI cells. Resolved versions and runtime dependency audits are retained per profile; transitive packages are not all tested at their individual minima. These are configured checks, not an assertion that pending CI has passed. Require results at the exact preparation head and final protected-main commit. See the [MCP guide](../mcp.md#sdk2-compatibility-candidate) for the client/protocol fixtures and limits.

The 64 KiB result cap remains an upper bound, not a promise to accept every smaller result. SDK 2 includes modern server-identity metadata in sizing even on legacy connections, so near-limit results may be conservatively refused. Inner project result JSON and approval/submission/consumption/ACK distinctions remain unchanged. No new native-agent, SSH, Windows, live OAuth or pre-existing-database qualification is claimed. #387/#388 and research drafts #246/#248 remain outside this release scope.
