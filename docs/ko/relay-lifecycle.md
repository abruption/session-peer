# 릴레이 라이프사이클 강화 (개발)

이 변경 사항들은 #69를 위해 개발 중입니다. 아직 배포된 RC가 아니며, 24시간 운영 게이트나 실제 OAuth 제공자 검증을 통과하지 않았습니다.

## 안정적인 디바이스 및 명시적 로테이션

초기 인증서 지문은 논리적 디바이스 ID로 유지됩니다. 공개 키 버전에는 별도의 지문과 세대가 부여됩니다. 정책, 라우트 및 요청 영수증은 수신자 키 변경 전반에 걸쳐 논리적 ID에 연결된 상태를 유지합니다. 추가적인 SQLite 마이그레이션은 기존 v0.9 신원과 영수증을 보존합니다.

로테이션을 수행하기 전에 디바이스 수신자 및 해당 상태를 사용하는 다른 명령을 중지하십시오:

```sh
session-peer device rotate --state /private/device-state \
  --operation-id REPLACE-WITH-A-FULL-UUID --route direct
session-peer device rotation-status --state /private/device-state
```

응답 유실로부터 복구할 때는 작업 ID를 유지하십시오. 알 수 없는 결과를 해결하기 위해 새 로테이션을 시작하지 마십시오. 페어링된 모든 피어는 명시적으로 구성된 도달 가능한 수신자 라우트를 보유해야 하며 `identity-rotation-v1`을 지원해야 합니다. 기존 `device routes` 명령으로 라우트를 업데이트하십시오. 수신자는 오프라인 클라이언트에서 자신의 핀을 투명하게 로테이션할 수 없습니다. 먼저 해당 클라이언트 수신자를 온라인 상태로 전환하십시오.

Prepare 단계는 고정된 TLS를 통해 이전 키를 증명하고 새 키로 생성된 서명을 검증합니다. Commit 단계에는 새 키 TLS 연결이 필요합니다. 전환 기간 동안 대기 중 및 폐기된 키는 프로브, 영수증 상태 확인 및 로테이션 조정 접근 권한만 가집니다. 이전에 커밋된 구 키는 10분의 복구 창을 가지며 메시지를 제출할 수 없습니다. 취소는 이 복구 창보다 우선합니다. 새로운 요청과 충돌이 발생하더라도 동일한 세대에 대해 두 번째 로테이션을 생성할 수 없습니다. 로컬 활성화는 기록된 모든 피어가 커밋한 후에만 수행됩니다. 실패한 시도는 동일한 제안과 개인 키를 유지합니다.

디바이스 상태 잠금은 일반 명령이나 수신자가 상태를 점유하고 있는 동안 로테이션/백업을 배제합니다. 별도의 수신자 잠금은 두 개의 로컬 수신자 프로세스가 동일한 상태를 사용하는 것을 방지합니다. 이들은 로컬 파일시스템 잠금이며 분산 리스가 아닙니다. 실행 중인 신원을 두 번째 머신에 복사하는 것은 지원되지 않습니다.

## 저널 한도 및 복구

```sh
session-peer device diagnostics --state /private/device-state
session-peer device backup --state /private/device-state \
  --policy /private/policy.json --out /private/new-snapshot
session-peer device restore --state /private/new-restored-state \
  --backup /private/new-snapshot
```

Diagnostics는 전역 10,000개 요청 한도, 남은 행 수, 보류 중인 알 수 없는 결과, SQLite/WAL 크기 및 여유 디스크 공간을 보고합니다. 알림, 경고 및 심각 임계값은 70%, 85%, 95%입니다. 용량이 가득 차면 새 제출이 거부되지만, 기존 영수증 및 관리 기능은 계속 사용할 수 있습니다. 공간을 확보하기 위해 영수증 증거가 정리되는 일은 결코 없습니다. 용량 예약과 영수증 생성은 트랜잭션으로 처리됩니다.

백업은 배타적 상태 잠금을 필요로 하며 신원 버전, 정책, 일관된 SQLite 스냅샷 및 매니페스트를 포함합니다. 출력 결과는 키가 포함된 비공개 **암호화되지 않은 스테이징 디렉터리**입니다. 보관을 위해 승인된 암호화 백업 시스템을 사용하십시오. 소스 제어를 통해 디렉터리를 공개하거나 이동하지 마십시오. 상태를 백업해도 릴레이나 OAuth 제어 서비스로 키가 복사되지는 않습니다.

복원은 비공개 스테이징 디렉터리를 준비하고, 영구 복구 마커를 커밋한 후에만 대상 위치를 원자적으로 게시합니다. 중단된 스테이징은 사용할 수 없습니다. 기존 영수증은 계속 쿼리할 수 있습니다. 누락된 영수증은 미실행을 증명하기보다는 알 수 없음을 반환합니다. 발신 및 수신 전송, 키 로테이션 변경 및 새로운 페어링/등록은 모두 계속 차단됩니다. 영수증 상태 쿼리는 계속 사용할 수 있습니다. 이 안전장치를 해제하는 단일 명령 재정의는 존재하지 않습니다. 복구를 계획하기 전에 스냅샷 이후의 네이티브 효과를 조정하고 기존 신원을 취소/격리하십시오. 이 개발 구현체는 아직 완전한 키 분실 복구 워크플로를 제공하지 않습니다.

## 제어 데이터베이스 업그레이드

제어 데이터베이스에는 Better Auth 스키마와 별도로 자체 마이그레이션 원장이 있습니다. 신규 설치와 스키마가 바뀌는 모든 업그레이드는 HTTP 서비스를 시작하기 전에 컴파일된 마이그레이션을 명시적으로 실행해야 합니다:

```sh
node dist/server/migrate.js
```

먼저 발행자와 릴레이를 중지하고 격리하십시오. SQLite 데이터베이스, 서명 키, 공개 상태 및 재생 최고 수위 상태를 포함하는 보호된 일관성 스냅샷을 만든 다음, 제어 서비스 신원으로 정상 보호 설정과 배타적 writer lock을 사용하여 명령을 실행하십시오. 마이그레이션은 트랜잭션 방식이며 멱등성을 보장하고, 안정적인 principal, 세대, 취소 tombstone, 작업 영수증 및 단조 증가 공개 리비전을 보존합니다.

정상 시작은 검증만 수행합니다. 오래되었거나 부분적이거나 미래 버전이거나 손상된 스키마는 DDL을 실행하지 않고 `migration_required`로 실패합니다. 마이그레이션을 `ExecStartPre`에 추가하거나, 마이그레이션 원장을 삭제하거나, 실패 후 이전 스냅샷을 자동 복원하지 마십시오. 스택을 중지한 상태로 유지하고 격리된 복구를 검토하십시오.

## 선택적 제어 서비스 어드미션

독립형 정적 토큰 릴레이는 계속 사용할 수 있습니다. 제어 서비스 관리형 릴레이는 다음을 사용합니다:

```sh
session-peer relay serve --auth-state /run/session-peer-auth/state.json \
  --auth-issuer https://relay.example.com \
  --auth-replay-state /private/relay-state/spent-tickets.json --bind 127.0.0.1 --port 3769 --seconds 0
```

`--auth-state` 및 `--accounts`는 상호 배타적입니다. 읽기 전용 상태에는 검증 공개 키와 최소한의 디바이스 소유권/취소 기록이 포함됩니다. 엔드포인트 개인 키, 로그인 세션 토큰 및 OAuth 제공자 시크릿은 포함되지 않습니다.

어드미션에는 유효 기간이 짧은 ES256 티켓과 등록된 P-256 디바이스 키의 서명이 필요합니다. Audience, issuer, generation, owner, receiver 및 room이 검사됩니다. 기존 1회용 WebSocket 쿠키를 발급하기 전에 티켓이 1회 소비됩니다. 상태가 누락되었거나 유효하지 않으면 장애 시 닫힘(fails closed) 방식으로 작동하며, 기존 연결은 매초 취소 여부를 재확인합니다. 제어 서비스 발급과 Python CLI는 픽스처 통합을 통과했습니다. 토큰 검증 테스트만으로는 실제 브라우저 로그인이 작동함을 입증하지 못합니다.

### 호스팅 용량 및 운영자 메트릭

호환 기본값은 명시적으로 설정할 수 있습니다:

```sh
session-peer relay serve ... \
  --handshake-rate 20 --pending-sessions 100 \
  --global-connections 10 --user-connections 8 --device-connections 4 \
  --connection-byte-budget 33554432 --metrics-port 3768
```

모든 값에는 하한과 상한이 있습니다. 기기별 용량은 사용자별 용량을 초과할 수 없고, 사용자별 용량은 전역 용량을 초과할 수 없습니다. 잘못된 조합은 시작을 거부합니다. 속도 초과는 429를 반환합니다. 대기 세션 또는 연결 용량 초과는 새 어드미션 증명을 소비하거나 이미 발급된 1회용 세션을 버리지 않고 503을 반환합니다. 기본값은 안전 한도이며 지원 사용자 수 보장이 아닙니다. 측정된 systemd 메모리, task 및 파일 디스크립터 한도 아래로 유지해야 합니다.

선택적 메트릭 리스너는 별도 포트의 `127.0.0.1`에만 바인딩됩니다. 이를 리버스 프록시하지 마십시오. 제어 서비스는 고정된 비식별 스키마를 읽어 기존 Authelia 보호 운영자 경계를 통해서만 노출합니다. 현재 연결, 대기 room, 대기 세션, 어드미션 및 용량 거절, 전달 프레임/바이트, 가동 시간과 설정 한도를 보고합니다. 사용자, room, principal, ticket, proof, 주소 또는 내용은 보고하지 않습니다.

## 브라우저 로그인 (통합 후보)

```sh
session-peer device login --state /private/device-state --server https://relay.example.com
session-peer device enroll --state /private/device-state --name laptop --operation-id FULL-UUID
session-peer device pair --state /private/device-state --invite /private/invite.json --route relay --login
session-peer list --device DEVICE-ID --device-state /private/device-state --relay-login --output-format json
```

헤드리스 로그인은 `--no-browser`를 사용합니다. 출력된 URL을 별도의 브라우저에서 열고 해당 사용자 코드를 확인하십시오. 비공개 디바이스 코드와 그 결과 생성된 세션 토큰은 출력되지 않습니다. 로그인은 명시적 디바이스 디렉터리에 비공개 0600 파일로 저장됩니다. 만료된 로그인은 또 다른 명시적 로그인을 필요로 합니다. 핵심 로컬/SSH 명령은 로그인을 시작하거나 이 서비스에 접근하지 않습니다.

제어 서비스는 GitHub/Google과 함께 Better Auth를 사용하며, `control/` 아래에서 독립적으로 소유됩니다. Python 클라이언트와 서비스 API는 언어 간 픽스처 통합을 통과했습니다. 전용 제공자 자격 증명이 준비되어 있으며, 실제 OAuth 검증은 아직 보류 중입니다. 단위 테스트를 정상 작동하는 공개 로그인으로 보고해서는 안 됩니다.

제어 서비스 관리형 로테이션의 경우 `--login`을 `device rotate`에 추가하십시오. 이는 이전/새 키 증명과 안정적인 작업 ID를 사용하여 스테이징된 공개 키를 제어 서비스에 등록한 다음, 독립적인 고정 엔드포인트 전환을 완료하는 동안 외부 어드미션에 해당 새 키를 사용합니다. 실패 후에는 동일한 작업 ID를 재사용하십시오.

릴레이는 쿠키를 발급하기 전에 사용된 JWT ID를 커밋하고 재시작 전반에 걸쳐 이 작은 재생 파일을 보존합니다. 페이로드는 유지하지 않습니다. 제어 공개 상태는 60초마다 새로고침되고 180초 이내에 만료됩니다. 상태가 누락되었거나 만료되었거나 유효하지 않은 경우 어드미션을 거부하고 기존 관리형 연결을 닫습니다.

관리형 어드미션은 또한 기존 전역 10개 연결 한도 내에서 한 사용자당 8개, 한 디바이스당 4개의 열린 릴레이 연결로 제한합니다. 공개 상태에는 영구적으로 증가하는 리비전이 포함됩니다. 릴레이는 가장 높은 리비전을 기억하여 재시작 후에도 동일한 리비전에서의 롤백이나 충돌하는 내용을 거부합니다. 이 최고 수위선은 사용된 티켓 파일과 함께 유지되며 제어 상태 복구 중에 폐기되어서는 안 됩니다.

운영자는 서비스 신원으로 재생 상태를 한 번 초기화해야 합니다:

```sh
session-peer relay init-replay --out /private/relay-state/spent-tickets.json
```

이는 어떠한 파일도 덮어쓰지 않습니다. 어드미션은 이 명시적 초기화 후 최소 65초 이후에 발급된 티켓만 수락합니다. `serve`는 누락된 재생 상태의 재생성을 거부합니다. 자동 재시작 훅에 초기화를 포함하지 마십시오. 상태 유실 후에는 명시적 복구 전에 제어 권한을 조정/격리하십시오. 사용된 티켓 ID는 빠르게 만료되지만, 동일한 파일이 제어 리비전 최고 수위선도 유지하므로 서비스의 수명 동안 보존되어야 합니다.

## KR 서비스 백업 및 복원 스테이징

배포된 KR 서비스는 암호화된 Restic 작업 전에 `deploy/ops/abruption-kr/session-peer-backup-snapshot.py`를 사용합니다. 이 헬퍼는 조정된 스택을 잠시 중지하고 트랜잭션 측면에서 일관된 제어 데이터베이스, 어드미션 서명 키, 제공자 구성, 공개 인증 상태 및 릴레이 재생/최고 수위 파일을 포함하는 루트 전용 복구 세트를 생성합니다. 스냅샷을 공개하기 전에 데이터베이스 무결성과 서명 키의 게시된 JWK를 검증한 다음, 이전에 활성화되어 있던 스택을 복원합니다. 부분 스냅샷은 DR 작업을 중단시킵니다.

Restic 범위에는 변경 불가능한 제어 및 릴레이 런타임, 준비 상태 헬퍼 및 설치된 서비스 유닛도 포함됩니다. 복구는 먼저 격리된 루트 전용 디렉터리에 복원한 후 스냅샷 매니페스트, 파일 해시 및 모드, SQLite 테이블 수, 상태/재생 리비전, 사용된 항목, 서명 키 및 런타임 링크를 검증해야 합니다. 실행 중인 서비스에 직접 덮어쓰거나 이전 제어 데이터베이스, 서명 키 또는 재생 최고 수위를 자동으로 승격하지 마십시오. 프로덕션 교체에는 여전히 중지된 스택과 명시적인 롤백/취소 격리가 필요합니다.
