# 명시적 Codex wake

## 연속 wake 제한

CLI와 MCP는 큐 제출 전에 `SESSION_PEER_WAKE_DEPTH`와 `SESSION_PEER_WAKE_ORIGIN`을 읽습니다. 각 wake는 단계를 하나 늘리고 원본 UUID를 유지합니다. 기본 한도는 3단계이며 초과하면 제출 없이 `wake_depth_exceeded`를 반환합니다. 운영자는 `--wake-max-depth` 또는 `SESSION_PEER_WAKE_MAX_DEPTH`로 0–16 범위에서 명시적으로 낮추거나 높일 수 있습니다. 0은 wake를 비활성화합니다. 잘못되거나 불완전한 문맥은 제출 전에 `invalid_wake_context`로 거부합니다. 일반 전송은 기존처럼 큐에만 제출합니다.

소유한 app-server에는 증가한 문맥을 전달합니다. SSH는 환경 변수 전달 설정 없이 형식이 검증된 문맥을 전달하며, 목적지는 받은 한도를 낮출 수 있지만 높이지 못합니다. 여러 목적지는 원본 식별자를 공유하되 예산은 독립적입니다. MCP는 시작 시점의 환경을 읽으며 호출 스레드의 신원을 인증하지 않습니다. Wake는 큐 메시지 앞에 진단용 표시를 붙이고, 제출 또는 정상 dry-run 이후 `depth`, `origin`, `maxDepth`를 담은 `wakeProvenance` 결과를 추가합니다. 표시도 32 KiB 메시지 제한에 포함됩니다. 표시와 본문은 권한을 부여하지 않으며, 단계를 복원하려고 큐·기록·대화 본문을 읽지 않습니다.

비활성 대상의 활성화는 정규 홈과 스레드별로 60초당 3회가 기본입니다. 운영자가 관리하는 `SESSION_PEER_WAKE_TARGET_RATE`는 0–16을 받으며 0은 비활성 대상의 활성화를 막습니다. 예약은 기존 wake 잠금 아래 저장됩니다. `wake_rate_exceeded`는 큐 제출 전에 거부하고, 읽을 수 없거나 너무 크거나 잘못된 상태는 `wake_rate_state_invalid`로 거부합니다. 실패·중단된 시도도 예약을 유지하고 시계가 뒤로 움직여도 보수적으로 유지합니다. Dry-run과 활성 상태가 확인된 작성기는 활성화 예산을 쓰지 않습니다. 기존 `wake_in_progress`와 `already_active` 동작은 유지됩니다. 대상·호스트별 예산은 독립적이고 운영자나 같은 사용자 프로세스가 협조적 상태를 초기화할 수 있으므로 전역 비용 한도나 호출자 인증은 아닙니다.

고정된 Codex 0.154.0 소스에서 셸의 `inherit="all"`은 제외 규칙이나 `include_only`가 없으면 이 변수를 유지하며, `inherit="core"`와 `inherit="none"`은 명시적 설정 없이는 제거합니다. 기본 비밀 이름 필터에는 걸리지 않습니다. stdio MCP의 기본 허용 목록에는 없으므로 새 MCP 프로세스에는 `env_vars` 전달을 명시해야 합니다. 기존·공유 MCP 프로세스는 나중 호출자의 환경을 받지 못합니다. 정적인 `env` 설정은 문맥을 초기화하거나 충돌시킬 수 있습니다. 필터로 문맥이 사라지면 새 로컬 원본을 만들므로 전역 단계 한도를 보장할 수 없으며, 로컬 활성화 제한은 별도의 보완책입니다. 승인·프로필·네이티브 환경 정책은 자동 변경하지 않습니다.

격리된 하위 프로세스 테스트는 상위 소스의 규칙을 모사하고 CLI·MCP·SSH 문맥과 app-server 대체 프로세스의 환경을 검증합니다. 인증된 네이티브 셸·MCP 클라이언트·모델 턴은 실행하지 않으며 0.154.0 이후 버전의 wake 지원 근거는 아닙니다. 출처: [고정된 셸 정책](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/protocol/src/shell_environment.rs), [고정된 MCP 환경](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/rmcp-client/src/utils.rs), [현재 구성 설명서](https://developers.openai.com/codex/config-reference/).

`session-peer send --to codex:<uuid> --wake --wake-timeout 30 "message"`

일반 전송은 큐 전용으로 유지됩니다. Wake는 대상의 기존 구성에 따라 모델 사용량을 발생시키고 세션 기록 및 프로젝트 파일을 수정할 수 있습니다. 수명 주기 및 네이티브 작성기 배제가 테스트된 버전인 macOS/Linux 및 **Codex CLI 0.154.0**이 필요합니다. 다른 버전은 독립적으로 검증될 때까지 안전하게 실패(fail closed)합니다. 이 버전 경계는 wake에만 적용됩니다.

운영자는 평소와 같이 `--codex-home` 및 SSH `--host`를 선택할 수 있습니다. 원래 작업 디렉터리는 해당 홈의 저장된 스레드 레코드에서 가져옵니다. 누락되었거나, 보관되었거나, 초기화되지 않았거나, 소유자를 알 수 없거나, 디렉터리를 사용할 수 없는 대상은 큐 추가 전에 거부됩니다. 상태/큐 DB는 직접 수정되지 않습니다. session-peer 가드는 동일한 정규 홈 및 UUID에 대한 wake 요청을 직렬화하며, 네이티브 Codex의 작성기 잠금 또한 무관한 동시 재개로부터 보호합니다.

## 네이티브 수명 주기

`codex exec resume UUID`는 0.154.0에서 프롬프트를 요구하며 입력을 추가하지 않고는 큐를 활성화할 수 없습니다. Wake는 대신 네이티브 `codex app-server`를 시작하고 stdio 프로토콜을 초기화한 다음 정확한 UUID와 원래 cwd로 `thread/resume`을 호출합니다. 재개 자체는 대기 중인 큐 메시지를 소비합니다. session-peer는 `turn/start`를 호출하거나, 메시지를 프롬프트로 복사하거나, 스레드를 포크하거나, 작성기 잠금을 해제하거나, 신뢰/샌드박스/승인 구성을 변경하지 않습니다. 대화형 승인 요청은 명시적으로 실패합니다. app-server API는 실험적이며, 다른 CLI 버전을 지원하려면 반복 검증이 필요합니다.

이미 활성화된 작성기는 하나의 큐 제출을 수신하며 두 번째 프로세스는 시작되지 않습니다. 비활성 대상의 경우 wake는 마감 시간(기본 30초, 범위 1~60) 내에 하나의 네이티브 턴이 완료되기를 기다립니다. 그런 다음 소유한 프로세스 그룹을 종료합니다. 이것은 지속적인 백그라운드 워커가 **아니며** 전체 큐를 비우겠다는 약속도 아닙니다. 오래 실행되는 턴은 타임아웃 시 중단될 수 있으며 부분적인 작업이 남을 수 있습니다. 기존의 활성 프로세스는 절대 종료되지 않습니다.

SSH 대상에서도 동일한 수명 주기와 타임아웃이 실행됩니다. 연결 유실이 미전달을 증명하지는 않습니다. 원격 wake는 호출자의 연결이 끊어지더라도 자체의 제한된 수명을 갖습니다. 취소 시 소유한 프로세스의 정상적인(graceful) 종료를 시도한 후 강제 정리를 수행합니다. 자동 재전송은 발생하지 않습니다.

## 결과

기존 제출 필드는 그대로 유지됩니다: `submitted`, `queueId`(네이티브 큐가 반환하는 경우), `codexHome`, `status`, `consumptionConfirmed`. 별도의 `wake` 객체에는 `status`, `reason` 및 확인된 경우 `cwd`가 포함됩니다.

- `validated`: dry-run 전용이며 아무것도 큐에 추가되거나 시작되지 않았습니다.
- `already_active`: 메시지가 큐에 추가되었고 기존 작성기는 계속 실행 중입니다.
- `completed`: 네이티브 재개 턴이 완료되었습니다.
- `refused`: 안전/사전 점검 요구사항이 충족되지 않았습니다.
- `failed`: 네이티브 트랜스포트, 재개, 승인 또는 턴 실패입니다.
- `timed_out`: 소유한 활성화가 마감 시간을 초과하여 정리를 시도했습니다.
- `unknown`: 중단되었거나 모호한 활성화 결과입니다.

제출은 성공하면서 wake는 실패할 수 있습니다. 이 경우 CLI 종료 코드는 0이 아니며 JSON은 큐 ID, `submitted: true` 및 실패를 유지합니다. **자동으로 재전송하지 마세요.** `completed`는 특정 큐 항목이 수신되었다는 증거가 아닙니다. `consumptionConfirmed`는 계속 false로 유지됩니다. 이전에 큐에 들어간 항목이나 다른 동시 제출이 완료된 턴일 수 있습니다.

MCP의 경우 대상 기능에 `send`와 `wake`를 모두 추가한 다음 `send_message(..., wake=true, wake_timeout=30)`을 호출하세요. 전송 권한만으로는 wake가 부여되지 않습니다. 클라이언트의 MCP 타임아웃을 전체 큐/SSH/wake 예산 이상으로 구성하세요(예: 150초). 그렇지 않으면 클라이언트 타임아웃으로 인해 제출된 결과가 가려질 수 있습니다.

## 검증 증거

CLI 0.154.0이 설치된 mac-mini-m4에서 새 프롬프트 없이 app-server를 통해 격리된 테스트 스레드가 초기화, 중지, 큐 추가 및 재개되었습니다. 네이티브 turn-start/turn-complete 이벤트가 관찰되었습니다. 첫 번째가 동일한 UUID를 보유하고 있는 동안 두 번째 app-server 재개는 `already has an active writer`로 실패했습니다. 구현된 CLI는 통제된 다른 메시지에 대해 `submitted: true`, 큐 ID 및 `wake.status: completed`를 반환했습니다. 프로젝트 신뢰 또는 승인 우회 플래그는 사용되지 않았습니다.

자동화된 테스트는 픽스처 SQLite 데이터베이스, 실제 권고 잠금(advisory lock) 및 네이티브 프로세스 대역을 사용합니다. 비활성/활성/보관된/누락된 대상, 기본 큐 전용 동작, 마감 시간 및 승인 실패, 프로세스 정리, 동시 가드 거부, 중단된 제출, 원격 부분 결과 보존 및 별도의 MCP 권한을 다룹니다. 실시간 모델/SSH 확인은 수동으로 진행되며 공개 CI는 모델 자격 증명을 받지 않습니다.

실제 Codex 0.154.0 MCP 클라이언트는 원격 Orca 사용자 지정 홈을 사용하여 로컬 list/send/wake 및 mac-mini → macbook list/send/wake를 완료했습니다. 원격 기본 홈은 인증이 취소된 상태였으며, 큐에 들어간 제출과 실패한 네이티브 턴은 인증을 변경하거나 재전송하지 않고 부분 실패로 보존되었습니다. 로컬 및 KR SSH Claude 프로토콜 테스트 인박스 또한 실제 Codex MCP 클라이언트로부터 각각 하나의 메시지를 수신했습니다. 이들은 전용 프로토콜 픽스처였으며 프로덕션 Claude 대화가 아니었습니다.

예상대로 초기 비대화형 Codex 테스트는 기존 승인 정책에 따라 쓰기 도구를 거부했습니다. 성공한 테스트에서는 테스트 클라이언트의 `mcp_servers.session_peer.tools.send_message.approval_mode="approve"`를 명시적으로 설정하고 서버 정책에서 테스트 대상만 허용했습니다. 배포된 플러그인은 이 승인 재정의를 설정하지 않습니다. 플러그인 마켓플레이스 등록 및 설치는 일회용 CODEX_HOME에서 검증되었으며 프로덕션 플러그인 구성은 건드리지 않았습니다. 실시간 wake는 macOS에서 테스트되었으며, Linux 프로세스/잠금 동작은 자격 증명이 있는 모델 실행이 아닌 CI 픽스처로 처리됩니다.

macOS/Linux 정리는 그룹 리더를 회수하기 전에 소유한 프로세스 그룹에 TERM 후 KILL을 보내며 TERM을 무시하는 자식도 포함합니다. 정리 후 그룹 ID를 재사용하지 않습니다. 별도 세션으로 이탈하거나 원격에서 실행되는 프로세스는 범위 밖이며, 이미 제출된 요청을 철회하지 않습니다.
