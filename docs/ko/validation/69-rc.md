## 로컬 발견 사항 및 수정 사항

독립적인 온톨로지 검토를 통해 세 가지 실패 사례가 재현되었다. 격리 전 상태가 복원에 의해 노출될 수 있었고, 복원된 발신자가 여전히 전송/순환할 수 있었으며, 누락된 릴레이 재생 파일이 자동으로 재생성될 수 있었다. Python 수정 `52d32c6`은 게시 전에 복원을 단계화하고, 발신자 및 수신자 복구 경계를 모두 검사하며, 명시적인 지속성 재생 초기화를 요구한다.

회귀 테스트 범위에는 중단된 복원, 유지된 상태 조회, 누락/손상된 재생 상태, 부트스트랩 티켓 펜싱, 사용된 티켓 영속화 실패, 재시작 간 퍼블릭 상태의 롤백 검사도 포함된다. 동일한 머신의 최고 수위 표식으로는 모든 권한 기관의 완전한 머신 롤백을 감지할 수 없으므로, 호스트 손실 복구에는 여전히 외부 조정/펜싱이 필요하다.

본 수정 후 로컬 macOS/Python 3.13 실행 결과: 399개 발견된 테스트 중 396개 통과, 공통 API 계약 대기 중으로 3개 Node 통합 테스트가 명시적으로 건너뛰어짐. Wheel 및 sdist 빌드 통과. 초기 Node 후보는 macOS에서 타입 검사/빌드 및 31개 테스트를 독립적으로 통과했으며, KR은 Linux ARM64 Node 22/24에서 동일한 31개 테스트를 보고했다. 이러한 수치는 실시간 OAuth 또는 모델 검증이 아니다.

정확한 Python 커밋 `52d32c6` 역시 아카이브되어 릴레이 및 MCP 추가 구성요소가 포함된 격리된 KR Ubuntu ARM64/Python 3.12 가상 환경에 설치되었다. 해당 환경에서 396개 테스트가 모두 36.611초 만에 통과했다. 테스트 로그를 보존한 후 임시 소스/환경은 제거되었다. 이 실행에는 모델 호출, 프로덕션 수신기, 릴레이 서비스 또는 Caddy 변경이 포함되지 않았다.

`tests/test_control_integration.py` 아래의 Node/Python 테스트는 폐기 가능한 시드 세션을 사용하여 실제 제어 애플리케이션, Better Auth, SQLite 및 암호화를 사용한다. 루프백 HTTP 브리지는 외부 TLS 전송만을 대체한다. 프로덕션 애플리케이션에는 테스트 인증 엔드포인트가 추가되지 않는다. 통합 후보는 초기에 3가지 테스트를 통과했다: 0세대 등록/허가/취소, 커밋 응답 유실 및 네이티브 효과 중복 제거가 포함된 관리형 키 순환, 소유자 간 수신기 거부. 공유 계약은 첫 번째 등록 시 expectedGeneration을 생략하고, 첫 번째 순환 시 expectedGeneration=0/신규 generation=1을 사용한다. 완료된 과거 작업은 소유자 전용 영수증을 통해 조정된다.

이후 macOS 후보 실행에서는 통합이 활성화된 401개 Python 테스트 전체, 52개 Node 테스트, 타입 검사/빌드 및 프로덕션 npm audit(보고된 취약점 0건)을 통과했다. 프로듀서 회귀 테스트에는 제한적 umask, 별도 DB 재시작, 가시적 게시 후 디렉터리 fsync 실패, 리비전 소진 및 복원된/누락된 리비전 거부가 포함된다. Google 부트스트랩 테스트에는 부분 쓰기/파일 fsync/링크 실패, 모호한 디렉터리 영속성 및 명시적 운영자 확인이 포함된다. 이는 픽스처 결과이며 실시간 제공자 로그인이 아니다.

이후 네 번째 교차 언어 테스트에서 관리형 허가 → 쿠키 → WebSocket → 고정된 엔드포인트 TLS → 네이티브 픽스처의 전체 경로를 통과했다. 캡처된 릴레이 프레임에는 마커가 포함되지 않았으며, 제어 취소 시 이미 열려 있던 발신자 연결이 닫히고 해당 릴레이 슬롯이 해제되었다. 외부 네트워크 TLS만 루프백으로 리디렉션되었으며, 이것이 퍼블릭 WSS를 증명하지는 않는다. 새로운 wheel 및 sdist 코어 설치도 버전/도움말 스모크를 통과했으며, 추가 구성요소가 없는 스위트는 338개 테스트를 통과했다(8개 선택적 모듈 건너뜀).

KR 프로듀서 작업 df66f9a/1336ee0은 퍼블릭 디렉터리 권한 및 리비전 장애 테스트를 제공했으며, 이는 Python 생성 계약 및 기존 퍼블릭 파일 롤백 보호와 통합되었다. 최종 통합 후보는 여전히 독립적인 Linux 검증 및 실제 샌드박스 배포가 필요하다.

추가 콜백 회귀 테스트에서 계정 생성 및 로그인이 거부되었음에도 불구하고 허용 목록에 없는 아이덴티티가 고아 사용자 행을 남기는 현상이 재현되었다. 이제 GitHub 및 검증된 Google 사용자 정보 핸들러 모두 Better Auth가 사용자를 생성하기 전에 불변 프로바이더 허용 목록을 확인하며, 데이터베이스 훅은 두 번째 경계로 유지된다. 회귀 검증문은 두 프로바이더 모두에 대해 변경되지 않은 사용자/계정/세션 수를 다룬다. KR의 후속 3de5604는 인증서 기반 초기 주체 검증 및 채워진 사전 계약 후보 상태를 거부하는 스키마 마커에도 기여했다. 그 결과 Node 스위트는 55개 테스트를 통과했고 4개의 Python 통합 케이스도 모두 다시 통과했다. 이러한 발견 사항은 실제 OAuth 배포를 위한 이전 후보를 대체한다.
## 독립적인 Linux 및 서비스 증거

KR은 Linux ARM64에서 정확한 후보 `54f09f6`을 독립적으로 검증했습니다.
Node 22.23.2 및 24.16.0은 각각 npm ci, typecheck, build, 52개 테스트 및
프로덕션 종속성 감사를 통과했습니다(보고된 취약점 0건). Python 3.12.3은
당시 유효했던 3개의 Node 통합 테스트가 활성화된 상태에서 401개 테스트 전체를 통과했습니다. 기존
KR 소스 브랜치는 변경되지 않은 상태로 유지되었습니다. 이는 이후의 OAuth 및
초기 주체(initial-principal) 수정이 아닌 해당 이전 후보에 대한 증거입니다.

최신 프로덕션 코드 후보 `9c62f9e`는 macOS에서 402개의 Python 테스트,
55개의 Node 테스트, typecheck/build 및 wheel/sdist 빌드를 통과했습니다. 해당 4개의 통합 테스트에는
관리형 WebSocket 경로가 포함됩니다. 최신 KR 서비스 샌드박스는 컴파일된 마이그레이션,
루프백 health/UI/Host 및 비인증 검사, 교차 UID 준비 상태(cross-UID readiness),
명시적 재생(replay) 초기화, 재생 보존, 리비전 증가 및 종속성 시작/중지 동작을
별도로 통과했습니다. 제공자 전송(provider-transport) 픽스처는 18개의 OAuth/디스커버리 테스트를
통과했으며, 실제 제공자 로그인은 아직 테스트되지 않았습니다.

샌드박스에서 두 가지 배포 요구사항이 확인되었습니다. Node 실행 파일은 보호된
홈 경로 외부에 있는 루트(root) 소유의 일반 런타임이어야 하며, 릴레이(relay) 재생 상태는
DynamicUser 최상위 심볼릭 링크 대신 전용 하위 디렉터리를 사용해야 합니다.
스테이징된 유닛들은 이에 맞게 조정되었습니다. 현재 제어(control) 장애 시 릴레이가
중지되며, 제어 복구만으로는 릴레이가 재시작되지 않았습니다. 수동 시작을 자동 복구로
취급하지 않고 자동 복구는 여전히 게이트로 유지됩니다. 샌드박스 유닛 및
리스너는 중지/제거되었으며, 공유 Caddy 구성은 변경되지 않고 유지되었습니다.
이러한 검사에는 프로덕션 OAuth 자격 증명이나 실제 에이전트 세션이 아닌,
합성(synthetic) 자격 증명과 격리된 상태가 사용되었습니다.

이후 최신의 정확한 후보 `9c62f9e`는 독립적인 KR Linux ARM64 검증을
통과했습니다. Node 22.23.2 및 24.16.0은 각각 클린 설치, typecheck, build,
55개 테스트 및 보고된 취약점 0건으로 프로덕션 감사를 통과했습니다. Python 3.12.3은
당시 유효했던 4개의 통합 케이스를 포함한 402개 테스트 전체를 35.992초 만에
통과했습니다. 소스 바이트, 록파일(lockfile) 및 기존 KR 브랜치가 보존되었습니다.
이러한 결과는 macOS의 2차 실행이 아닌 독립적인 KR 세션에서 나온 것입니다.

이후의 테스트 전용 확장은 관리형 WebSocket 경로 자체에서 로테이션을 실행합니다.
엔드포인트가 키 변경을 커밋한 후, 픽스처는 응답을 반환하기 전에 실제
WebSocket을 닫습니다. 작업 ID(operation ID)를 재사용하면 제어 영수증(control receipt)과
엔드포인트 상태가 조정(reconcile)되고, 새 키가 활성화되며, 네이티브 메시지
영수증이 보존됩니다. 동일한 메시지 ID를 재전송해도 총 하나의 효과만 발생합니다.
4개의 집중 통합 케이스는 macOS에서 5.267초 만에 통과했습니다. 의도적인
복구 단계는 릴레이의 초당 20회 핸드셰이크 예산을 초과하도록 간격을 두었으며,
프로덕션 속도 제한은 상향 조정되거나 우회되지 않았습니다. 이 픽스처는 여전히
외부 TLS를 루프백으로 대체하며 공용 WSS나 OAuth를 설정하지 않습니다.

**2026-09-18 14:38:54.010369 UTC**(23:38:54 KST)에 종료되었습니다.

성공, 65회의 새 메시지 및 65회의 중복 성공, 772회의 공용 WebSocket
업그레이드가 기록되었습니다. 기록된 실패, 안전 실패 및 샘플 간격은 0건입니다.

로컬 론처/엔드포인트 하네스와 KR 옵서버 서비스/타이머가 중지되었습니다.
이전 재인증 일정은 캠페인과 함께 취소되었으며, 이번 인계로 추가 테스트나
자격 증명 갱신은 예정되어 있지 않습니다. KR 제어/릴레이 서비스는

## 최종 RC 재실행 — 9월 19일 (24시간 테스트 제외)

사용자는 연속 24시간 테스트만 제외한 완전한 RC 재실행을 요청했습니다.
최종 후보는 macOS Python 3.14.7 환경 및 배포된 KR 서비스에 대해 테스트되었습니다.
제어 프로젝트는 `npm ci`, typecheck, build, 8개 파일의 63개 테스트 및
보고된 취약점 0건으로 `npm audit --omit=dev`를 통과했습니다. Python 스위트는
실제 컴파일된 Node 제어 통합이 활성화된 상태에서 405개 테스트 전체를 통과했습니다.
새로운 sdist 및 wheel이 빌드되었습니다. wheel은 릴레이 및 MCP 추가 구성요소(extras)와
함께 새 가상 환경에 설치되었고, `pip check`를 통과했으며, 설치된 CLI는 0.9.0을 보고했고
클린 홈(clean-home) 목록 스모크 테스트를 통과했습니다. KR에 대한 SSH 기반
소스 스트림 실행은 구조화된 성공 목록을 반환했습니다.

재실행 과정에서 두 가지 Antigravity 1.2.7 호환성 문제가 드러나 수정되었습니다.
네이티브 `agentapi send-message` 명령은 더 이상 수신자 및 메시지 위치 인자 앞에
추가 `--`를 허용하지 않습니다. 또한 브리지는 로캘 형식의 `ps lstart` 문자열을
비교했기 때문에, 한국어 TUI에서 시작된 브리지는 릴레이 워커가 C 로캘을 사용할 때
사라졌습니다. 이제 해당 명령은 문서화된 위치 인자를 사용하며 프로세스 시작
식별 정보는 항상 `LC_ALL=C`로 읽힙니다. 정확한 argv 및 안정적인 로캘 회귀 테스트가
추가되었습니다. 이제 통합 목록 테스트는 선택적인 라이브 Antigravity 등록을
명시적으로 격리하며, 이전 Claude 권한 오류 테스트는 현재의 fail-closed 디스커버리
규약에 맞춰 조정되었습니다.

각 네이티브 시도마다 새로운 고유 요청 ID가 사용되었습니다. Claude 2.1.277,
`gpt-5.6-sol high`를 사용하는 격리된 Codex 0.155.0 세션, Gemini 3.8 Flash High를
사용하는 Antigravity CLI 1.2.7에 대해 동일 Mac 직접 및 공용 릴레이 전달이 통과했습니다.
각 공용 릴레이 교환에서 수신자 연결(attachment) 및 네이티브 제출 또는 큐 수락이
관측되었습니다. 각각의 정확한 마커는 해당 어시스턴트 또는 모델 트랜스크립트에
한 번씩 나타났습니다. 이러한 트랜스크립트 관측 결과는 독립적인 증거로 유지되며,
제품 API는 계속해서 `consumptionConfirmed=false`를 보고합니다.

오류 주입(fault injection) 직전, control, readiness, relay 및 stack 유닛이
활성 상태였고, health는 200을 반환했으며, 공용 상태/재생 최고 수위(high-water) 리비전은
모두 1183이었습니다. 전체 프로세스 `SIGSTOP`이 구성된 30초 watchdog을 트리거했습니다.
35.67초 만에 control이 새 PID로 재시작되었고, readiness가 다시 실행되었으며,
수동 복구 없이 relay가 새 PID로 재시작되었습니다. 구성 해시는 변경되지 않은 채
유지되었으며, 상태 및 재생 리비전은 퇴보 없이 1185로 진행되었고, 두 루프백 리스너가
모두 복귀했으며, health는
200. 복구 후 새로운 Claude 공용 릴레이
요청은 하나의 정확한 트랜스크립트 ACK를 수신했습니다. 최종 유휴(idle) 샘플에서
control은 11개 작업과 함께 약 39.8 MiB를 사용했고 relay는 1개 작업과 함께
약 19.8 MiB를 사용했습니다. 연결된 3769/3770 연결은 없었습니다. 최근의 세 가지
control 경고는 예상된 주입된 watchdog 타임아웃, SIGKILL 및 결과 실패(failed-result)
기록이었으며, relay에는 경고 수준의 라인이 없었습니다.

이전 섹션의 실제 GitHub 및 Google 콜백, 제공자 소유자 격리, 네이티브 장치 인증,
등록/조정(enrollment/reconciliation), 페어링된 공용 WSS/E2EE, 유효하지 않은 증명 및
재생 거부, 활성 연결 취소 증거는 변경되지 않고 배포된 백엔드에 계속 적용됩니다.
최종 재실행에서는 제공자 동의를 반복하거나 제공자 ID를 변경하지 않았습니다.
병합(merge), 릴리스 태그 생성, 패키지 게시 또는 24시간 캠페인은 수행되지 않았습니다.

## KR 부팅 활성화 및 인프라 재부팅 — 9월 19일

`session-peer-stack.target`은 부팅 정책에서 `multi-user.target`을 통해서만 활성화됩니다.
제어 및 릴레이 서비스는 직접적인 부팅 진입점으로 비활성화된 상태를 유지합니다.
타깃이 제어를 시작하고, 기존의 Upholds, readiness, Requires 및 BindsTo 관계가
제어 → readiness → 릴레이 순서를 확립합니다. 마이그레이션 및 재생 초기화는
수동의 비활성 단발성(one-shot) 작업으로 유지되며 부팅 종속 항목이 아닙니다.

실제 KR 호스트 재부팅으로 부팅 ID가
`2537e227-6dc3-4137-85c6-bd253e4f8e5f`에서
`5523b4cb-68d6-40a0-8987-b1cf084857f6`으로 변경되었습니다. SSH는 약 28초 만에 복귀했습니다.
제어는 12:37:38 KST에 시작되었고, 12:37:49에 상태 확인 및 상태 게이트를 통과했으며,
readiness가 완료되었고, 수동 개입 없이 12:37:49에 릴레이가 시작되었습니다.
4개의 스택 유닛 모두 재시작 0회 및 실패한 시스템 유닛 없이 활성 상태였습니다.
공용 상태 확인 및 로그인은 200을 반환했습니다. 비인증 세션 및 챌린지 요청은
각각 401과 403으로 계속 거부되었습니다.

인증 상태 리비전은 1205에서 1207로 진행되었습니다. 재생 파일은 사용된 2개의 항목과
원래의 `notBefore`를 유지한 다음, 릴레이 시작 시 최고 수위 리비전을 1185에서
1207로 진행했습니다. 재부팅 중에는 마이그레이션, 재생 초기화, 자격 증명 교체 또는
데이터베이스 초기화가 실행되지 않았습니다.

부팅 후 기존 인프라를 확인했습니다. Caddy, Authelia, Authadmin, Ontology,
포트폴리오 대시보드, 서버 모니터, Orca, Redis, 두 rclone 마운트, Tailscale,
SSH, OCI 모니터링 및 중앙 Vault 런타임이 활성 상태였습니다. 두 rclone 마운트는
마운트되어 읽기 가능한 상태였습니다. 공용 ontology, chat, login 및 status
라우트는 예상대로 302/200/200/302 상태를 반환했고, `vault
status` reported `integrity=ok`를 보고했습니다. 컨테이너는 예상되지도 실행되지도
않았습니다. 유일한 부팅 경고는 기존의 커널/플랫폼 및 OCI 유닛 모드 경고였으며,
부팅 시 실패한 유닛은 발생하지 않았습니다.

기존 KR Restic 작업에는 처음에 session-peer 경로가 없었습니다. 첫 번째 콜드
스냅샷 시도는 타깃을 중지해도 즉각적인 검사 전에 제어가 비활성화되지 않아
fail-closed 방식으로 실패했습니다. 스냅샷이나 원격 백업은 생성되지 않았으며,
헬퍼의 정리 작업으로 4개 유닛이 모두 복원되었습니다. 수정된 헬퍼는 역순으로
relay, readiness, control 및 타깃을 명시적으로 중지하고 내구성 있는 상태를
읽기 전에 이들 모두가 비활성 상태가 될 때까지 대기합니다.

수정된 실행을 통해 콜드 스냅샷 `20260919T034516Z`가 생성되었습니다. SQLite 무결성은
`ok`였습니다. 2개의 장치, 2개의 작업 영수증, 2명의 사용자 및 4개의 세션이
존재했습니다. 공용 상태 리비전은 1214였고, 재생 최고 수위는 사용된 두 티켓을
모두 유지한 채 1213이었습니다. 그리고 허가 서명 키(admission signing key)는
게시된 JWKS와 일치했습니다. 스냅샷 이후 스택은 마이그레이션이나 재생 초기화
없이 정상(healthy) 상태로 복귀했습니다.

이후 정상적인 암호화된 R2 작업이 종료 코드 0(exit zero)으로 완료되었고 Restic
스냅샷 `d286abf2841aa5ef6bc92b00d0b6cadc34b441ef51fdaa12c043011a3482eb42`를
저장했습니다. 해당 범위에는 콜드 스냅샷, 보호된 제어 구성, 4개 유닛 전체,
헬퍼, readiness 코드 및 불변 제어/릴레이 런타임이 포함됩니다. 보존 및 prune
이후 저장소 사용량은 공유된 10 GiB 허용량 중 0.9407 GiB였습니다.

해당 정확한 R2 스냅샷이 루트 전용의 격리된 디렉터리에 복원되었습니다. Restic은
총 180.638 MiB에 달하는 3,742개 항목을 다운로드했습니다. 명시된 10개의 지속성
파일 및 모드, SQLite 무결성 및 테이블 수, 서명 키/JWKS 일치 여부, 2개의 장치,
2개의 영수증, 공용 리비전 1214, 사용된 항목 2개를 포함한 재생 리비전 1213,
필수 유닛/헬퍼 및 두 릴리스 심볼릭 링크 모두에 대해 검증을 통과했습니다.
이 테스트는 프로덕션 경로에 쓰기 작업을 수행하지 않았습니다. 복원된 사본은
이후 제거되었습니다. 라이브 DB 무결성은 `ok`로 유지되었고, 스택은 정상 상태를
유지했으며, 실패한 유닛은 발생하지 않았습니다. 이제 매일 05:00 작업에서
