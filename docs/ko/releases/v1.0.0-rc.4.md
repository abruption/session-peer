# session-peer v1.0.0-rc.4

RC4는 부분 게시된 RC3를 새 버전으로 수정 발행합니다. PyPI는 RC3 wheel을 수락했지만 sdist 업로드는 HTTP 502 응답이 반복돼 실패했습니다. RC3는 정식 버전 승격에 사용할 수 없습니다. RC4는 패키지 버전과 릴리스 문서만 변경하며 런타임 동작은 검토된 #162 및 #168 구현과 같습니다. 명시적으로 시험판을 테스트하지 않는 안정 버전 사용자는 v0.9.2를 유지하십시오.

## RC2 이후 변경 사항

- #162는 실패 시 닫힌 경로 계약을 유지하면서 시도별 비식별 단계와 선택적 진단 이벤트를 추가합니다. control/admission 설정 재시도는 애플리케이션 제출 전에만 제한적으로 수행하며 메시지는 재전송하지 않습니다.
- #168은 정상 idle 만료 뒤 수신자 재연결 지연을 0.5초로 유지하고, Relay 레그에 10/10초 ping을 사용하며, receiverRoleBusy 및 clientRoleBusy 카운터를 추가합니다.
- #163 오프라인 재현은 정체된 경로의 증폭 감소를 보여 줄 뿐, 경로 자체의 복구나 #161 해결의 증거가 아닙니다.

## 완전 게시 후 설치

두 페어링 엔드포인트에서 기존 패키지 관리자로 정확한 후보를 설치하십시오. 다른 설치 관리자로 바꾸거나 RC3의 불완전한 파일 집합에서 설치하지 마십시오.

```bash
# Unix / WSL with relay and MCP
pipx install 'session-peer[relay,mcp]==1.0.0rc4'
# Native Windows core and MCP, without relay
pipx install 'session-peer[mcp]==1.0.0rc4'
```

Python/PyPI 버전은 1.0.0rc4, GitHub 태그는 v1.0.0-rc.4입니다. 코어는 Python 3.9+, MCP는 3.10+, 수신자/Relay 런타임은 Unix 또는 WSL의 3.11+가 필요합니다.

서비스 환경: launchd나 systemd로 시작한 macOS·Linux 수신자는 대상 TUI의 `codex` 실행 파일 디렉터리가 `PATH`에 있어야 하며, 그렇지 않으면 Codex 전달이 `native_outcome_unknown`으로 실패합니다. RC4 재검증은 수신자 서비스 `PATH`에 그 디렉터리만 추가한 뒤 운영 실패 없이 완료됐습니다. [페어링 기기 가이드](../paired-devices.md), #171, #176을 참고하십시오.

## 증거와 남은 조건

RC2의 4시간 캠페인은 완료 기록 없이 172분에 끝났습니다. 정확히 완전 게시된 RC4가 5개 호스트 검증을 통과할 때까지 #161, #163 및 #164를 열어 두십시오. posted 또는 queued는 소비된 ACK가 아닙니다. 독립 관측이 없으면 `consumptionConfirmed: false`가 올바른 결과입니다.

## 게시 후 검증 계획

1. 게시된 태그와 커밋, PyPI 파일 두 개의 해시, wheel 및 sdist 신규 설치, 시험판 상태와 안정판 v0.9.2의 latest 상태를 확인합니다.
2. Mac mini, MacBook, quintet-desktop(네이티브 및 WSL), KR, US에 정확한 RC4를 설치하기 전에 설치 파일과 승인된 일관 상태 스냅샷을 백업합니다. 기기 신원, 정책 및 재생 방지 상태를 보존합니다.
3. 독립 프로세스에서 complete 또는 aborted 기록을 남기는 #164의 5개 호스트 4시간 캠페인을 실행합니다. 매분 health, 수신자별 5분 이상 간격의 probe, 진단 이벤트, 분 단위 receiverRoleBusy/clientRoleBusy, T0/T2h/T4h 독립 ACK, T2h Relay 재시작 후 60초 이내 복구 목표가 포함됩니다.
4. 모든 실패를 단계별로 분류합니다. 설명되지 않은 실패, 누락된 ACK 또는 미완료 실행은 정식 승격을 막습니다. 게시나 PR 병합만으로 마일스톤을 닫지 마십시오.

## 릴리스 경계

준비만으로 게시 또는 전체 기기 검증이 완료되지 않습니다. Antigravity는 실험적이며 호스팅된 Relay/OAuth 상태는 패키지 가용성과 별개입니다. 결과가 불명확한 메시지를 재전송하거나 ACK를 강제하려고 수신 권한을 변경하지 마십시오.
