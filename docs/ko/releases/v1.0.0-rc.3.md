# session-peer v1.0.0-rc.3

준비된 후보이며 배포 공지가 아닙니다. RC3는 RC2 계약을 유지하고 #161에서 추적 중인 간헐적 공개 릴레이 경로 실패를 대상으로 합니다. 명시적으로 시험판을 테스트하지 않는 안정 버전 사용자는 v0.9.2를 유지하십시오.

## RC2 이후 변경

- #162: 경로 실패는 `no_authenticated_route`, `retryAllowed: false`, `consumptionConfirmed: false`를 유지하면서, 시도마다 정제된 단계·사유·경과 시간과 WebSocket 종료 코드·출처를 보고합니다. control 및 admission 설정 timeout은 애플리케이션 제출 전에 새 admission으로 한 번만 재시도하며, 에이전트 메시지는 절대 재전송하지 않습니다.
- #162: 선택형 `--diagnostic-events`는 메타데이터만 담은 수신자 생명주기 이벤트와 릴레이 방 이벤트를 출력하고, 릴레이 지표에 방·attach·만료 카운터가 추가됩니다. 진단은 기본적으로 꺼져 있습니다.
- #168: 1초 이상 열려 있던 대기 방이 릴레이에 의해 정상 종료되면 수신자는 백오프를 늘리지 않고 0.5초 뒤 다시 연결합니다. 릴레이 레그는 10초 WebSocket ping 간격·제한을 사용하므로 정체된 레그를 약 40초가 아닌 약 20초 안에 감지합니다.
- #168: 릴레이 지표에 거절된 중복 레그를 세는 `receiverRoleBusy`와 `clientRoleBusy`가 추가됩니다.
- #163의 오프라인 루프백 재현에서 이 변경이 정체된 경로를 증폭하는 재연결 공백을 줄이는 것을 확인했습니다. 정체된 네트워크 경로를 고치지는 않으며 #161이 해결됐다는 증거도 아닙니다.

## 업그레이드 참고

- 스키마·상태·정책 마이그레이션은 없습니다. 기기 신원, 핀, 영수증, 톰스톤과 재전송 방지 상태를 보존하고, 상태를 삭제하거나 결과를 알 수 없는 메시지를 다시 보내지 마십시오.
- 릴레이와 페어링된 양쪽 엔드포인트를 같은 버전으로 업그레이드하십시오. 새 지표와 이벤트는 추가형이며 [페어링 기기 가이드](../paired-devices.md)를 참고하십시오.
- 네이티브 Windows 코어와 MCP는 계속 지원됩니다. 수신자/릴레이 런타임은 Unix 또는 WSL과 Python 3.11+가 필요합니다.

## 배포 후 설치

페어링된 양쪽 엔드포인트에서 같은 패키지 관리자와 정확한 버전을 사용하십시오. 기존 관리형 설치는 기존 환경 안에서 업그레이드하고 다른 설치 관리자로 바꾸지 마십시오.

```bash
# Unix / WSL with relay and MCP
pipx install 'session-peer[relay,mcp]==1.0.0rc3'
# Native Windows core and MCP, without relay
pipx install 'session-peer[mcp]==1.0.0rc3'
```

Python/PyPI 버전은 `1.0.0rc3`이고 GitHub 태그는 `v1.0.0-rc.3`입니다. 의존성 없는 코어는 Python 3.9+, MCP는 Python 3.10+가 필요합니다.

## 검증 증거와 남은 조건

RC2의 4시간 관찰은 완료 기록 없이 172분에 중단됐고 공개 릴레이 실패가 기록됐으므로 통과한 soak가 아닙니다. 오프라인 재현은 메커니즘을 입증할 뿐 실제 장애 원인을 확정하지 않습니다.

게시된 정확한 RC3가 5개 호스트 관찰을 통과할 때까지 #161, #163, #164를 열어 두십시오. `posted`나 `queued`를 소비로 간주하지 마십시오. 독립적으로 관찰된 ACK가 없으면 `consumptionConfirmed: false`가 사실 그대로입니다.

## 배포 후 검증 계획

1. 게시된 정확한 태그·커밋, wheel·sdist 해시와 새 설치를 검증하십시오. GitHub는 Latest가 아닌 prerelease로 유지하고, 안정 업그레이드는 계속 v0.9.2를 선택해야 합니다.
2. Mac mini, MacBook, quintet-desktop(네이티브 및 WSL), KR, US에 정확한 RC3를 설치하기 전에 설치 파일을 백업하고 승인된 일관 상태 스냅샷을 사용하십시오. 운영 신원과 재전송 방지 상태를 보존하고 설치 관리자를 조용히 바꾸지 마십시오.
3. 항상 `complete` 또는 `aborted`를 기록하는 독립 감독 프로세스로 5개 호스트 4시간 관찰(#164)을 수행하십시오. 매분 상태 확인, 같은 수신자에 대한 probe 간격 5분 이상의 직접·릴레이 probe, `--diagnostic-events` 활성화, 매분 `receiverRoleBusy`와 `clientRoleBusy` 기록, T0/T2h/T4h 새 토큰의 독립 ACK, 60초 이내 회복을 목표로 한 T2h 릴레이 재시작 1회를 포함합니다.
4. 실패는 진단 단계별로 기록하십시오. 설명되지 않은 실패, 누락된 ACK, 완료되지 않은 관찰은 승격을 막습니다. PR 병합이나 PyPI 게시만으로 RC3 마일스톤을 닫지 마십시오.

## 릴리스 경계

- 준비 단계는 태그, 게시, 장비 교체, 운영 재시작을 승인하지 않습니다. 이는 승인을 받아 별도로 실행하십시오.
- Antigravity는 계속 실험 단계입니다. 호스팅 릴레이/OAuth 상태는 패키지 게시와 무관합니다.
- ACK를 얻기 위해 수신 권한을 바꾸거나, 모호한 전송을 재시도하거나, 보고서에 자격 증명을 노출하거나, 피어 요청을 사용자 직접 승인으로 간주하지 마십시오.
